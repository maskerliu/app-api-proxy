## 二、十二个主题族

### 族 1 · 代理转发内核（10-30 → 11-11）

**产出**
- 转发必须**还原原始请求**（方法、头、体、query 编码与顺序），否则被代理应用行为漂移；响应回写要独立于记录写入，记录失败不能吞掉响应。
- 响应体乱码根因是**解压与字符集解码未做**，不是编码显示问题。
- 每次注册成功生成**新 uid**，代理与 Mock 记录按 uid 隔离，避免同一 uid 重复注册串数据。
- 构造测试记录的注入方式：`POST https://localhost:8884/_proxy/<path>` + 头 `x-mock-uid` / `x-mock-host`。缺 `/_proxy` 前缀直接 404；上游不可达仍会产生 502 记录，可用来验证 UI。

**被修正过**：响应不返回且被代理方收不到；请求体显示用硬编码假数据；`saveProxyDelay` 不生效；延迟要按客户端作用域而非全局。

**保留的差异**：`parseProxyRequest` 刻意保留原始 query 顺序与编码、不走 `queryParts`；`parseLooseUrl` 不 trim、不把空串当 null。「三套 axios/http 转发合并成单点」**已废弃**——统计上报只发不收、`proxyCorsMedia` 是媒体透传，并入主转发会改变响应语义。

### 族 2 · 打包 / 发布 / 更新链路（10-30 → 11-17）

**产出**
- 增量更新写 `resources/app.asar` 需要**提权**：捕获 `EACCES`/`EPERM` 后走 elevate；重启用的 helper 必须无控制台窗口，且 UAC 取消与超时两条路径都要收尾。
- 发版一条命令：`yarn pub`（增量）/ `pub:full`（全量）/ `publish`，按目标形态生成 `version.json` 与 `version-<platform>-<arch>.json`。**两份版本文件必须同批改**，漏一份会导致「检查更新永远提示有新版本」。
- `updateUrl` 要用本机局域网出口 IP，不能用 `127.0.0.1`，否则局域网其他设备升级失败。
- 体积优化有效项：删未使用依赖、补 asar 排除规则。`LICENSES.chromium.html` 与 Electron 本体裁剪收益有限。

**被修正过（全部是环境而非代码）**
- `Cannot create symbolic link` → 本机需开 **Windows 开发者模式**，否则 7za 解 winCodeSign 包建不了 darwin 软链。
- `EBUSY: unlink app.asar` → 有实例在跑；另有一个隐蔽来源是 **Qoder 搜索索引守护进程**持有句柄，关掉它即可（会自动重启）。
- 并发跑两个 `yarn pkg` 会在 winCodeSign 缓存上互抢 rename。
- 打包后 exe 图标仍是 Electron 默认（rcedit 时序）。
- 下载进度条不更新、走到 99% 卡住；校验/落盘失败未通知渲染层。

### 族 3 · Mock 存储与数据模型演进（11-04 → 11-07）

**产出**
- 规则与记录**分文档**存储：单条记录可独立改，避免一个 rule 塞大量记录后全量重写。
- 同一规则内以 **url 为 key**，先查重再更新，冲突时覆盖——因此 `addRule` 与二维码的 `onRecordUpdate` 功能重复，保留一条。
- 记录改 UUID + 乐观锁（`expectedUpdatedAt`）+ 迁移；匹配引擎再引入**指纹唯一**（v3→v4）。
- **派生 match 发生在 `MockService.saveMockRecord`，不在仓库层**：新增直接调 `mockRepo.saveRecord` 而不带 match 的代码会落一条无 match 的记录。等价前提由单测锁住（`normalizeMatchRule(deriveMatch(x))` 与 `deriveMatch(x)` 深度相等）。
- 已迁移记录**不重算**，否则会覆盖历史撤销结果。

**被修正过**：打包版无法新增 Mock 规则（dev 正常）；本地服务启动会自动执行 schema 迁移并**改写真实用户目录**的 `biz_storage/Mock.Rules`——为验证 UI 而启动应用前必须先确认迁移可接受或已备份；`Only reserved document ids may start with underscore`。

### 族 4 · 需求 / PRD / 评审 / 复盘（11-05 → 11-19）

**产出**：7 份需求文档 + 一次完整演进复盘，方法论已固化为用户级 `product-manager` skill，本仓库基线事实固化在项目级 `app-api-proxy-prd` skill。

关键量化：R1 估算 15.5 → 19.5 → 24.5 → **32.0 人日**，差额全部来自契约桩、迁移压测、缓存接线、UI 细化——即自上而下估算的盲区。

**结论**：PRD 补充项不来自功能描述本身，而来自五类「只能从真实代码约束推出来」的东西——非功能边界、既有状态负债、状态一致性、可观测性、工程管理。初版没写的边界，实现时一定会以范围外补丁的形式回来。

**11-19 R4 导出：一条量级断言没做基准，就被当成需求照做了**。PRD/技术设计写「50MB 包一次性 stringify 峰值可达数百 MB」，R4C-06 因此实现为「分片拼接字符串」。基准（`test/bench/pack-export.bench.ts`，5,000 条 / 8KB 体 / 包 42.7MB）证伪了这条前提：

- **出口形态决定峰值下界，序列化写法不决定**。分片拼接 + 返回字符串 = 收尾活堆 +85.5MB；聚合成对象 + 一次 stringify = 同样 +85.5MB。省内存的唯一手段是把「返回字符串」换成「边拼边写盘」（+0.2MB，且与包大小无关）。
- **只按页采样会量出自假的结论**。每页交接量到的是聚合档 +44.6MB，看起来比流式档省一半——因为 stringify 发生在最后一页之后，从没被采样到。基准因此同时报 `liveMb`（每页）与 `endMb`（收尾），引用内存数字一律引 `endMb`。
- **RSS 单看全是噪声**。同一次跑：流式档 RSS +184.6MB 而活堆只有 +85.5MB，差额是基准自己每页现造 200 条 8KB 记录的分配抖动；落盘档 RSS +13.0MB 反而最干净。
- **闸门阈值要写成能表达真实断言的形式**。基准曾写过 `liveMb > budget * 2` 这条红线，它拦住的是一个完全合法的实现（85.643 > 85.506，比值 2.004）——分片缓冲 + join 副本本来就 ≈2× 包体积。现在改成正向断言：`file.endMb * 4 > stream.endMb` 即失败，意思是「落盘出口必须比字符串出口低一个量级」，这条才是裁决真正依赖的性质。定闸门前先问「合法实现会不会撞上它」。
- **一致性判据按 UTF-8 字节，不按 `.length`**。含中文记录名时 UTF-16 码元数 ≠ 字节数，落盘文件/上传体积/50MB 上限量的都是字节。
- **「取全部」不能借用带列表上限的入口**。全场景导出原先用 `MockRepo.search()`，而它有 `RULE_SEARCH_LIMIT = 15`——只按名称搜时静默漏导第 16 个之后的场景，且「场景数超过 15 就报错」这条断言把回归做成了永真。已新增 `listRules()`。
- 附带一条 IPC 纪律（**11-19 R4C-08 已落地**）：几十 MB 文本不跨进程传（structured clone 复制两遍），改由主进程写盘后只回 `{status, filePath}`——落为 `MAIN_API_CMD.SelectSavePath`（只弹保存框拿路径）+ `ExportMockPack`（边拼边写并回条数回执），保存框选项抽到 `src/main/misc/save-path.ts` 与 `SaveFileAs` 同源；渲染层判体积上限要按 413 状态码（服务端 `proxy.service.ts:126` 用 `resp.status(413)`，axios 对 4xx 不抛错要显式判），不依赖 `RequestError` 文案。
- **文档回写要按接口名 grep 一遍再落笔**。本轮把「IPC 拆两段」写进 PRD 后核对源码，发现那半个改动在并行 WIP 覆盖时丢了——树里只剩 `SaveFileAs` 一把原语，`selectSavePath` 全仓零命中。凭对话记忆写「已完成」会直接产出读代码对不上的文档；声称已落地的东西一律以 `grep` 命中为准，未命中的写成「未开工」。同一条纪律也管**编号**：本轮照上一轮对话里的卡号写落地状态，写到「R4C-10 渲染层上传通道」头上——那是已被替换的 v1.1 编号，按文件级拆解的 v2 里 R4C-10 是包级校验、通道归 R4C-27；引用他文卡号前先看一眼表头是哪一版。
- **性能承诺要按代价复核，不按收益**。技术设计 5.3 给导出写了「>5,000 显示耗时预估」，但预估要先完整遍历一遍全库，比写盘本身还贵；实测 5,000 条 / 42.7MB 落盘只用 283ms，预估换不来任何决策。落地改成写后按回执 `recordCount` 提示「已超过导入上限」，`MockPackService.estimate()` 保留但不再接线——设计文档里「显示预估」这类措辞在实现时要问一次「为了拿到这个数得付什么」。
- **设计表里「UI 上提示」那句是需求，不是修辞**（R4C-09）：技术设计 D2 的 C 方案从一开始就写着「Web 是本地/自建部署场景，体积风险由用户自担，UI 上提示建议改用桌面端」，但这半句一直没有落点，直到接 Web 分支才补上那行提示。补的时候又发现同一承诺的另一半（超 5,000 条告知条数）在 Web 分支兑现不了——HTTP 出口只回包文本、没有回执条数，为数一遍条数等于把上一批刚撤掉的写前预估请回来。两条纪律：① 备选方案表里带「提示 / 告知 / 展示」的句子，实现时逐句问「落在哪个界面、由哪个返回值喂」；② 同一功能的第二个出口接完才看得见两端能力差异，差异要写进设计文档（5.3「导出记录数」已注明条数提示是桌面端独有），不能只留在实现细节里。
- **「复用同一套判定」不等于「把外部对象原样递进去」**（R4C-11）：导入的条目级校验按卡片要求复用保存路径的 `validateMockRecord`，但那个函数认「没有 match、有 url」这条历史路径——它能这么认，是因为 `saveMockRecord` 紧接着会 `deriveMatch`（`mock.service.ts:249` 判、`:261` 归一化、`:262` 派生）。导入走仓库层，那次派生压根不存在，于是「同一套判定」在导入侧会放过一批写完根本不参与匹配的记录，症状正是风险表里那条「导入成功、一条不命中、全程不报错」。修法不是加检查，而是**按契约重建入参**：只把包声明的字段交给判定。同批另一条同源的小坑：`"records": ["hello"]` 里的 `'hello'.match` 是 `String.prototype.match`，原样透传会报出「pathType 不合法」这种指错方向的话。推论：**照设计文档里的流程图实现前先跟代码对一次顺序**——D8 的 `normalize → validate` 与保存路径相反，照图做就会接受编辑器保存不了的记录。
- **代码注释里预先写下的「这句人话由 X 给出」也是承诺**（R4C-10）：`base.router.parseMultipart` 放开 `allowEmptyFiles` 时注明「由包校验给出 `packEmpty` 这种能看懂的原因」，但包校验一直缺席，0 字节文件走到端点上拿到的是一个「成功的空结果」。实现包级闸门时先 grep 回这类注释，把它点名的错误码逐个兑现；同批暴露的另一处同源：桩端点在没接线前对任何文件都回空结果，坏包与空包在 UI 侧长得一模一样，接线时要连带把「过了闸门仍是桩」用断言钉住，后续卡填实现才会变红而不是被静默替换。
- **「重算某字段」不等于「写回某字段」：派生值只许有一个写入点**（R4C-12）：卡片写「归一化后重算 `matchFingerprint`」，最省事的实现就是把指纹塞回 `record.matchFingerprint`——而仓库层在 `mock.repo.ts:392` 每次保存都自己算，于是库里那条的指纹有两个作者，包侧那个还可能是旧算法的产物。落地的形状是**旁路字段**：`readMockPack().prepared[].fingerprint` 只服务预览查重（R4C-13），`record.matchFingerprint` 保持不写。同批另一条边界：`sha1` 在 `mock.docs.ts:112`（主进程），共享层要能被渲染层 import，所以「谁算指纹」这件事同时被语义（单写入点）和物理（模块能不能引内建）约束着，两头都要查。判据：见到「补齐 / 重算 / 刷新 X」先 grep `X =`，命中两处就必须在文档里写死哪一处是权威。
- **一条记录可以既「被补齐」又「完全合法」，所以补齐说明不能进失败明细**（R4C-12）：卡片写「缺失字段回落并计入 issues」，照做的话结果页会把「包没写 id，我们补了」计成一条失败，而那条记录其实导进去了。现在 `issues` 只装「这条被跳过」，回落走新通道 `notes` + 码 `packFieldDefaulted`，断言钉住两者的坐标集合互不重叠。**新增明细码之前先问它属不属于「失败」那一族**——注意族名靠不住：`MOCK_PACK_CODES` 现在同时装包级失败和回落说明，判据是它进哪条通道，不是它在哪个常量数组里。
- **别凭印象给「另一个函数的行为」写断言**（R4C-12）：我按记忆认定 `normalizeMockRecord` 会用 `source.url` 回填 `match.pathOriginal`，据此写了断言、还配了一句解释性注释——实际 `mock.validation.ts` 全文只在 `normalizeMatchRule` 里透传一次这个字段，压根没有回填。两条测试因此变红，而那句注释如果留着，下一个人会拿它当依据继续垒。纪律：**断言里凡是引用别的函数行为的，先跑一次那个函数或 grep 它的实现**，注释只能写在实测之后；错误的注释比没有注释更贵。同一条纪律在文档侧的旧版见本节「文档回写要按接口名 grep 一遍再落笔」（R4C-08）。
- **把「不许做 X」做成「拿不到做 X 的东西」**（R4C-13）：预览的出口标准是「只读不落库」。先写成的是一句断言（假仓库的写方法被调了就抛），后来发现更硬的是入参类型——`previewMockPack(source: MockPackSource, …)` 那个接口只有五把读原语，写得动的东西压根递不进来。类型是结构事实、写探针是第二重、调用序列是第三重；只有前一种在重构时不会悄悄失效。**同类教训**：`readMockPack` 三阶段零库调用也不是靠「记得别查库」，而是那一层根本没有仓库依赖。
- **卡片写的折叠口径与明细的用途冲突时，按用途定**（R4C-13）：卡上写「明细仅前 200 条 + 同类原因折叠」，直觉实现是每个原因留几条再凑满 200。但明细存在的意义是让人**照着它去改那个文件**，重排过一次就等于把他指向另一条记录。定稿：按包内顺序取前 N，总数另报（`issueTotal`/`conflictCount`/`noteTotal`），不额外带原因分布 map——列出的这 N 条本来就看得见分布，要逐条核对的人手里有原文件。
- **`_id` 全局唯一而指纹查重是规则级：预览只能报它看得见的冲突，看不见的那半必须写下来**（R4C-13）：合并模式按目标场景建 `{byId, byFingerprint}` 两张表，「包里的 id 属于别的场景」这种必败情况在这一层完全不可见，要查全库 id 就得再读一遍全库。做法不是「顺手补上」也不是沉默，而是把这句写进函数注释与卡片遗留项，并注明它由 R4C-15 写库时被 PouchDB 顶回来。同理：「库内已有 + 待写入 > 上限」这个数响应体里也没有，宁缺不半套。
- **共享给多条用例的测试替身，累加的调用日志必须每条取走**（R4C-13）：`repo.calls` 挂在 describe 级，预览用例读了 `listRules` 之后，下一条「导入桩不碰仓库」的断言就拿着上一条的残留报错。加了 `takeCalls()`（取完即清），并且端点用例的调用序列断言从此只判自己那一次请求。**自检信号**：一条断言失败报出的实际值是**另一条用例**应该产生的，就是这个共享状态在漏。
- **「抽成纯函数供两条路径共用」的收口时点是第二条路径接上，不是函数就位**（R4C-14）：函数写完、`saveRecord` 改完，全工程仍然只有它一个调用方，卡片那句话在这会儿还不成立。落地状态必须写死「到哪一卡才真成立」，否则两种误读都会发生——下一个人看到新函数没人调，以为漏了接线；或者看到「已共用」，以为导入路径也已经过闸门。配套的边界：**纯函数化时把「模式决定」留在调用方**，ID 怎么分配、`createdAt` 是否沿用包值，是三条不同路径各自的决定，塞进组装函数就是把同一个决定做两次；留在外面的副作用反而更好——`Date.now()` 只剩一处，R4C-16 的注入点不会分裂。同批还有一条不并进来的判断：迁移 runner 里那段 doc 字面量看着重复，但它的输入是旧版 `jsonRequests` 而不是 `MockRecord`、`_id` 是 `rec_<sha1>`、时间戳是合成的 `now + idx`，硬套这把函数只会逼那条路径先伪造一个记录对象——**「形状像」不等于「输入同源」，合并判据先看参数从哪来**。
- **纯重构的验收要当场拿 HEAD 基线核对，不能引用上一批记录的数**（R4C-14）：卡片口径是「现有用例全绿 + diff 内无新增断言」，但在这个仓库里「无回归」还包括严格模式计数不许涨。上一批记的 186 不能直接拿来比——工作区常有并行 WIP，渲染层那几档随用户改动漂。做法：把本批两个文件复制出去、用 `git show HEAD:` 覆盖回来跑一次 `check:strict`、还原后再跑一次确认数字（186 → 184，两处都落在 `src/main/repository`，顺手证明搬家没带新债），还原后那次数字与本批结果一致才算还原成功。**判据**：任何「和上一批一样」的结论都要在同一份工作区里当场测出基线；跨批次引用的是记事，不是证据。另记一条同批踩到的纪律：改文档时把「目标代码被搬走」的锚点和「只是行号位移」的锚点分开处理——前者必须重指（旧位置已经没有那句代码，留着会误导），后者量大且无害，列成清单请裁决比逐处改写更诚实。
- **免启动 harness 会造出假信号**（R4C-08 渲染层验证，四条都让「不生效」的结论反转过）：① Vant 4 UMD 的全局名是 `window.vant`（小写），`app.use(Vant)` 静默无效，页面照常渲染但组件全是未知元素；② 只设 `--van-font-size-md` 会漏掉读 `lg` 的容器（`.van-dialog` 正文取 `--van-dialog-font-size: var(--van-font-size-lg)`），于是「弹窗不跟随字号」是探针的错——harness 必须复刻 store 的整条字号阶梯与 `BASE_THEME_VARS`；③ 用 `offsetTop` 判换行、`offsetLeft` 判右对齐会被 `align="center"` 与不同 `offsetParent` 骗过，一律改 `getBoundingClientRect`；④ 弹窗进场动画带 `scale3d`，量终态要给 `.van-dialog` 关掉 `transition`。另外响应式文本换语言后同步测量必然读到旧值，要 `await nextTick()` 两次并强制重排。

### 族 10 · 请求密度可视化（11-17 → 11-18，探索型需求的失败样本）

四版方案：① 行内热力条替代圆点 → 回退；② 列表上方独立分桶色块条 → 被否（「不要单起一行，标识应体现在每条记录上」）；③ 固定 1s 时间分桶 → 被否（会把一簇请求从整秒边界劈开）；④ 常驻时间戳槽位 → 被否（URL 列被推右 50px）。

**定稿**：按相邻时间差**切波**（间隔 ≤500ms 同波、单波跨度上限 2s）+ Vant 语义三档（灰/绿/橙）+ 同波实线串联 + 时间戳浮在上留白带。

**可复用做法（比结论更重要）**
- 开放式视觉需求先给 3–4 个方向、标推荐、按改动面递增，用户会直接点。
- 阈值类常量一旦被用户在工作树里改过（300ms → 500ms），**单测步长要改读常量**，否则阈值一动就红。
- 同页新加浮层/绝对定位元素前先 grep 类名——`.snap-time` 与长连接行已有的 `.snap-time` 撞名，scoped 不隔离同文件，把 WS 时长抽出了文档流。
- 暗色验证要用 Vant 真实 `.van-theme-dark` 类，自己伪造 text/gray 变量会掩盖掉 `text-color-3` 的对比度问题。

### 族 11 · 媒体预览与编辑器（11-01 → 11-19）

**产出**：图片 / m4a / mp3 / wav / m3u8（HLS 经 `/corsMediaProxy`）/ SVG；大图按长宽规则缩放而非裁剪；预览信息浮层（尺寸、大小、编码）对齐关闭按钮；Ace 内容搜索 + 收起后变右上角悬浮放大镜。

**两条硬结论**
- SVG 预览要在 `mediaFormat` 里按文本头识别（`<svg`、`<?xml`、DOCTYPE 之后的 `<svg`），识别成 SVG 后把 blob 类型**补回** `image/svg+xml`——源站报 `octet-stream` 时 `<img>` 直接 onerror。
- **Ace 扩展必须静态 import**：core 按 `basePath` 懒加载 `ext-*.js`，打包后请求成 `https://localhost:9080/ext-searchbox.js` 而 404，功能静默失效且 dev 下看不出。另：`ace.edit(el)` 会清空容器 innerHTML，叠在编辑器上的自定义控件必须放在外层 wrapper。
- Ace **不观测自己的容器**：容器被布局改变后 `layerConfig.height` 停在旧值，只画得下旧行数且不报错，必须挂 ResizeObserver 调 `resize()`。

## 三、跨族规律

1. **「已承诺未实现」是本仓库最大的隐性范围**。WS 筛选图标、迁移复核页、命中解释都属于「后端齐、渲染层零调用」，验收链路断在最后一环。判断「未实现」必须查调用方，不能只看定义存在。
2. **概念分层不到位会反复制成 UI 债**。Mock 的「启用」曾经同时描述规则层（isMock）与记录层（activeVariantId），两层交叉直接导致用户问「怎么区分」，最后靠术语拆分（`servesVariant`）才解决。
3. **环境坑的密度高于代码坑**。打包/更新/验证三个环节里，八成「失败」是文件锁、权限、守护进程、开发者模式、端口残留，不是代码。
4. **越靠近用户的观感，验证成本越高**。凡「密度、对齐、紧凑、美观」类需求，平均 4–8 轮；凡有可量化判据（行高、左缘 x、computed style）的，一轮。差别不在描述精度，而在**有没有先把判据测出来**。
5. **文档里的量级断言是隐性需求**。「峰值可达数百 MB」「这条路径很慢」这类没有实测来源的话，会被实现方当作必须满足的约束照做，做错方向后再返工（见族 4 的 R4C-06）。凡写入设计文档的性能数字都要标数据来源；给不出基准的，写成「待测」而不是写成量级。
