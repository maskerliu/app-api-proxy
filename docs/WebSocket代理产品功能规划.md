# WebSocket 代理产品功能规划

> 关联文档：
> - [WebSocket 代理技术设计](./WebSocket代理技术设计.md)
> - [产品功能分析与需求规划](./产品功能分析与需求规划.md)
> - [PRD v1.1（0–6 周需求）](./PRD-v1.1-0-6周需求.md)
>
> 目标：把 WebSocket 从“列表里有一个没有数据的筛选图标”变成可观测、可解释、可 Mock 的完整调试能力，并与现有 HTTP 代理、Mock 规则、接入向导和诊断中心保持一致。

---

## 1. 背景与定位

### 1.1 为什么现在做

1. **产品债已经可见**：主界面保留了 WebSocket 筛选图标，使用说明也明确写着“不解析 WebSocket 帧”，新用户会误以为已经支持。
2. **真实研发场景高频**：IM、消息推送、订单状态、协同编辑、设备控制、直播互动都依赖长连接；只看 HTTP 会让代理在联调中“缺一条腿”。
3. **技术成本可控**：同端口 + `/_proxy` + `ws` 消息级中继即可覆盖主要场景，首版不需要自研帧解析或系统级抓包。
4. **与现有产品心智一致**：用户已经理解 `x-mock-host` / `x-mock-uid`、客户端选择、启用规则、录制→Mock 的闭环，WebSocket 可以复用同一套概念。

### 1.2 产品定位

WebSocket 代理是 AppApiProxy 的**协议补全**，不是新的抓包产品：

- 面向研发期联调：看握手、看消息、定位断线原因、造服务端推送。
- 与 HTTP 共用接入方式、客户端注册、规则体系和诊断入口。
- 首版强调“看得见、可解释、零侵入”，不追求逐帧字节级保真。
- Mock 能力从“握手级”逐步过渡到“消息级”和“场景级”，避免一次性做成通用 WebSocket 平台。

### 1.3 与现有路线图的关系

现有产品规划把 WebSocket/SSE 放在 Later。建议拆开处理：

| 能力 | 原规划 | 建议 | 理由 |
|---|---|---|---|
| WS 观测（连接/消息/诊断） | Later | 提前到 v1.1 之后的小版本 | 成本低、直接清产品债、补齐联调闭环 |
| WS 握手 Mock + 脚本推送 | Later | 与 Next 的“场景/状态机 Mock”合并规划 | 复用规则、录制、变体与启用机制 |
| WS 消息级 Mock + 回放 | Later | Next 后半段 | 依赖匹配引擎与规则编辑器稳定 |
| 协议解码/持久化/团队共享 | Later | 保持 Later | 避免过早背上协议与协作复杂度 |

结论：**先用一个轻量版本把 WS 变成“能看”，再让 WS Mock 搭现有 Mock 体系的便车，而不是单独发起一个大项目。**

### 1.4 设计原则

1. **零侵入观测**：只观测时，不修改、不重排、不丢弃业务消息；关闭压缩扩展只影响带宽，不改变消息语义。
2. **与 HTTP 一致**：同一端口、同一 `/_proxy`、同一 uid、同一客户端选择、同一启用规则。
3. **渐进 Mock**：先拒绝/伪造握手，再脚本推送，再消息规则，最后状态机。
4. **可解释**：连接失败、Mock 未命中、消息被截断/丢弃都要给出原因与下一步建议。
5. **有界**：连接数、帧数、单帧体积、推送频率都有上限，并在 UI 明示。
6. **不误伤业务**：断线、改写等控制动作必须二次确认；观测模式不得导致 App 连接异常。

## 2. 目标与指标

### 2.1 产品目标

| 目标 | 说明 |
|---|---|
| O1：让 WS 可接入 | 现有移动端/WebView/H5 用最小改动接入，10 分钟内看到第一条连接 |
| O2：让 WS 可观测 | 连接、握手、双向消息、关闭原因完整可见，可搜索与复制 |
| O3：让问题可解释 | 握手失败、证书、uid、上游拒绝、子协议不匹配都能定位 |
| O4：让推送可伪造 | 不依赖后端即可模拟握手、服务端推送、异常断线 |
| O5：让样本可复用 | 录制真实连接生成脚本，规则可导出/导入/回放 |
| O6：与 HTTP 形成闭环 | 同一规则、同一客户端、同一诊断中心，不形成第二套心智 |

### 2.2 成功指标

以 WebSocket 版本发布后 4 周为观察窗口：

| 维度 | 指标 | 目标 |
|---|---|---|
| 激活 | 安装到首条 WS 连接被记录 | ≤ 10 分钟，成功率 ≥ 60% |
| 激活 | 首条 WS 连接被记录到打开消息详情 | ≥ 70% |
| 价值 | 支持客户端（OkHttp/WebView/Node）握手记录成功率 | ≥ 95% |
| 价值 | 首条 WS Mock 命中耗时（WS-2 后） | ≤ 20 分钟 |
| 价值 | 录制脚本回放与真实消息序列一致率 | ≥ 98% |
| 留存 | WS 用户次周仍使用 WS 调试的比例 | ≥ 35% |
| 质量 | WS 观测导致的业务连接失败率 | ≤ 0.1% |
| 质量 | 消息展示延迟 p95 | ≤ 300ms |
| 质量 | 30 分钟、10 条连接、1 万条消息的额外内存 | ≤ 150MB |
| 体验 | 丢弃/截断提示可见率 | 100% |

### 2.3 护栏指标

- HTTP 代理、HTTP Mock、SockJS 推送回归为 0。
- 观测模式下不出现“代理自己断开业务连接”。
- 因 UI 卡顿导致的崩溃/无响应 < 0.5%。
- 任何截断、丢弃、限流都必须有可见提示，不允许静默丢失。
- WS Mock 未命中时不影响真实转发（默认回退上游）。

| 测试工程师 | 构造服务端推送、异常断线、弱网 | 脚本推送、关闭码、延迟 |

| 后端开发 | 确认客户端实际发送/接收内容 | 双向消息、搜索、复制 |

### 3.2 核心场景

| 编号 | 场景 | 当前痛点 | 目标体验 |

| S1 | 后端 WS 还没准备好，前端要先联调 | 只能等后端或写临时脚本 | 伪造握手 + 按脚本推送消息 |
| S2 | App 连不上 WS，只有“连接失败” | 不知道是 DNS/TLS/uid/上游拒绝 | 连接失败行直接给出阶段与原因 |
| S3 | 收到服务端推送后页面没更新 | 看不到消息内容与顺序 | 双向消息列表 + JSON 搜索 |
| S4 | 需要复现“下单后状态变更”推送 | 依赖后端触发 | 录制真实推送，一键回放 |
| S5 | 测试断线重连 | 只能拔网线/杀进程 | 指定关闭码断开连接，观察重连 |
| S6 | 后端改了协议字段 | 靠日志或抓包工具 | 搜索字段、对比前后连接 |
| S7 | 使用 Socket.IO/STOMP | 不知道代理是否支持 | 传输层可见，明确“未解码上层协议” |
| S8 | 团队成员要复现同一问题 | 口述消息内容 | 导出连接/规则，或直接复用规则包 |

## 5. 版本规划

### 5.1 WS-1：看得见（观测版，建议 v1.2）

**目标：** 让用户能接入、能看到一条完整连接，并知道失败原因；不改变业务消息。

**交付范围**

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| WS-01 | 同端口接入 | P0 | 复用 `/_proxy`，头与查询参数两种入口 |
| WS-02 | 接入向导 | P0 | OkHttp 拦截器、WebView/H5、Node `ws` 片段；含 `wss` 证书提示 |
| WS-03 | 连接列表 | P0 | `[WS]`、状态、时长、消息数、↑↓字节、客户端、Mock 标记 |
| WS-04 | 连接详情 | P0 | 握手请求/响应头、子协议、关闭码/原因、错误、连接元信息 |
| WS-05 | 消息列表与筛选 | P0 | 方向/类型/关键字、跟随最新、暂停跟随、清空 |
| WS-06 | 消息详情 | P0 | 文本、JSON 美化、二进制 base64/hex、复制 |
| WS-07 | 保留策略 | P0 | 连接数/帧数/单帧上限；丢弃与截断提示 |
| WS-08 | 锁定与暂停记录 | P0 | 长连接不被淘汰；暂停记录但保持转发 |
| WS-09 | 握手诊断 | P0 | 失败阶段与可执行建议 |
| WS-10 | 重连聚合 | P1 | 同 URL 30 秒内重连合并，可展开 |
| WS-11 | 连接导出/复制 | P1 | JSONL 连接文件、复制连接信息 |
| WS-12 | 手动断开 | P1 | 指定关闭码，二次确认 |

**关键体验**

- 接入：用户在向导中选择客户端类型 → 复制片段 → 扫码注册 → App 发起连接 → 列表出现 `[WS]` 行。
- 观测：点击连接 → 右侧摘要固定 → 消息列表内部滚动 → 点击消息看完整内容。
- 失败：连接行标红，详情直接显示失败阶段、目标、错误码与建议，不要求用户去翻日志。
- 长连接：可“锁定”或“暂停记录”，避免被 HTTP 请求或高频消息挤出。

**验收标准**

1. OkHttp（请求头）、WebView（查询参数）、Node `ws` 三种接入各完成一条连接记录。
2. 连接建立后 1 秒内出现在列表；消息展示延迟 p95 ≤ 300ms。
3. 双向消息方向、类型、大小、时间正确；二进制可复制为 base64。
4. 握手失败、上游 401/403/500、TLS 失败、缺少 host、uid 离线均有明确提示。
5. 30 分钟、10 条连接、1 万条消息：内存增量 ≤ 150MB，UI 可操作。
6. 截断/丢弃 100% 有提示；锁定连接不被淘汰。
7. HTTP 代理、HTTP Mock、SockJS 推送无回归。
8. 使用说明与接入片段更新，移除“不解析 WebSocket 帧”的旧限制。

**本阶段不做**

- 任何 Mock、改写、手动发送消息。
- 原始帧/分片/压缩细节。
- 协议解码、持久化、团队共享。

### 5.2 WS-2：造得出（可控 Mock，建议 v1.3）

**目标：** 不依赖后端即可模拟一条 WebSocket 连接和服务端推送，并能模拟异常断线。

**交付范围**

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| WS-13 | 拒绝握手 | P0 | 配置状态码、响应头、错误体 |
| WS-14 | 伪造连接 | P0 | 不连上游完成 101，配置子协议 |
| WS-15 | 脚本推送 | P0 | 连接后按延迟推送文本/二进制/关闭 |
| WS-16 | 录制生成脚本 | P0 | 从真实连接提取服务端消息、相对时间、截断信息 |
| WS-17 | 命中/未命中诊断 | P0 | 命中规则、相似规则、失败维度 |
| WS-18 | 协议维度隔离 | P0 | HTTP 规则不误命中 WS，反之亦然 |
| WS-19 | 断线模拟 | P1 | 关闭码/原因、立即断开、延迟断开 |
| WS-20 | Mock 变体 | P1 | 正常/空态/错误/断线/慢速，一键切换 |
| WS-21 | 延迟注入 | P1 | 握手与 Mock 消息延迟，不拖慢真实透传 |
| WS-22 | 记录入口 | P1 | 连接详情“录制到规则”，复用现有录制面板 |

**关键体验**

- 连接详情 → “Mock 这条连接” → 选择规则 → 选择模式（拒绝/伪造/透传）。
- 伪造模式提供模板：正常推送、空数据、错误码、断线、慢速。
- 录制一条真实连接后，自动生成“服务端消息脚本”；用户可删除消息、改延迟、改内容。
- 重新连接 App，直接命中 Mock；连接行显示 `[MOCK]`，消息标记来源。

**验收标准**

1. 20 分钟内完成“首条连接 → 创建 WS Mock → 命中”的闭环。
2. 拒绝握手能返回配置的状态码/头/体；客户端能收到真实 HTTP 错误。
3. 伪造连接能完成 101，并按脚本顺序与延迟推送消息；关闭码正确。
4. 录制脚本回放与真实序列一致率 ≥ 98%，允许 ±100ms 时序误差。
5. HTTP/WS 规则不互相误命中；切换启用规则对两者同时生效。
6. Mock 未命中时回退真实上游，并给出可解释诊断。
7. 断线模拟可指定 1000/1001/1011/1013 或强制断开，且二次确认。

**本阶段不做**

- 根据客户端消息内容自动回复（放 WS-3）。
- 状态机、变量、重连连续性。
- 手动发送消息。

### 5.3 WS-3：可复用（消息级 Mock 与回放，建议 v1.4）

**目标：** 让 WS Mock 从“单向播放”变成“可交互、可复用、可分享”。

**交付范围**

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| WS-23 | 消息回复规则 | P1 | 文本/二进制；equals/contains/regex/JSON Path；回复/关闭/忽略；once/持续 |
| WS-24 | 录制回放 | P1 | 原时序/压缩时序、循环/单次、暂停/继续 |
| WS-25 | 规则包导入/导出 | P1 | 规则包包含 WS 记录与脚本，往返无损 |
| WS-26 | 连接导出 | P1 | JSONL/结构化 JSON，包含握手与双向消息 |
| WS-27 | 消息 Composer | P2 | 手动发送文本/JSON/二进制，历史与重复发送 |
| WS-28 | 场景/状态机 | P2 | 连接→消息→回复→断开的步骤化场景，重连连续性 |
| WS-29 | 弱网模板 | P2 | 慢速推送、随机延迟、概率断线 |
| WS-30 | 断点/改写 | P2 | 暂停转发、修改单条消息后继续 |

**关键体验**

- 在规则管理器中新增“WebSocket”页签，与 HTTP 记录并列；规则详情显示“3 个 HTTP、2 个 WS”。
- 消息规则以“当收到…则…”表达，避免让用户写脚本。
- 录制回放可以“按原时序”或“压缩到 2 秒内”，适合演示与自动化测试。
- 场景以步骤列表呈现：连接、等待消息、推送、关闭；保留状态供重连使用。

**验收标准**

1. 消息回复规则在测试语料上命中率 ≥ 90%，once/持续语义正确。
2. 录制回放可暂停、继续、循环；时序误差在配置范围内。
3. 规则包导出→导入→启用后行为一致，WS 记录无丢失。
4. 连接导出可被同事导入查看（即使没有原始 App）。
5. 场景支持至少一次重连并保持状态。
6. 所有 Mock 动作都有命中解释与来源标记。

| 能力 | 说明 | 价值 |
|---|---|---|

## 6. 关键交互流程

### 6.1 接入流程

```
设置/接入向导 → 选择客户端类型
  → OkHttp / WebView / H5 / Node
  → 复制代码片段（含 x-mock-host / x-mock-uid 或 __mock_* 参数）
  → 扫码注册，确认客户端在线
  → App 发起 WS 连接
  → 列表出现 [WS]，向导标记“接入成功”
```

失败分支：

- 没有出现连接 → 提示检查代理地址、证书、拦截器是否覆盖 WS 握手。
- 出现失败行 → 直接跳到连接详情，展示失败阶段与建议。

### 6.2 观测流程

```
连接列表（筛选：全部/进行中/失败/已关闭/Mock）
  → 连接详情
    → 摘要：URL/状态/子协议/时长/字节/消息数
    → 握手 Tab
    → 消息 Tab：方向/类型/关键字 → 消息详情
    → 操作：复制、导出、锁定、暂停记录、断开
```

体验细节：

- 默认跟随最新；用户上滚自动暂停，出现“回到最新”。
- 选中消息后新消息不改变选中项。
- 锁定连接不参与淘汰；最多锁定 3 条，超出提示先解锁。
- 暂停记录只停止采集，不影响转发；恢复后从当前时刻继续，并插入“已暂停”分隔标记。

### 6.3 握手 Mock 流程

```
连接详情 → 创建/选择规则 → Mock 这条连接
  → 模式：拒绝握手 / 伪造连接 / 透传
    → 拒绝：状态码、响应头、错误体
    → 伪造：子协议、握手响应头、初始脚本
  → 保存并启用
  → App 重连 → 命中/未命中提示
```

### 6.4 脚本推送与录制回放

```
真实连接 → 录制到规则
  → 选择服务端消息（默认全选最近 N 条）
  → 生成脚本：时间、类型、内容、大小
  → 编辑：删除、改内容、改延迟、插入关闭
  → 启用 → 客户端重连 → 按脚本推送
```

### 6.5 消息规则流程

```
规则 → WebSocket → 新增回复规则
  → 条件：文本/二进制、equals/contains/regex/JSON Path
  → 动作：回复文本/二进制、关闭、忽略
  → 次数：仅一次 / 每次
  → 保存并启用 → 连接详情验证命中
```

### 6.6 故障模拟流程

```
连接详情 → 断开
  → 选择关闭码：1000 正常 / 1001 离开 / 1011 内部错误 / 1013 稍后重试 / 强制断开
  → 二次确认
  → 观察客户端重连、退避与错误提示
```

### 6.7 诊断流程

```
失败连接 → 详情
  → 失败阶段：解析 / DNS / TCP / TLS / 握手 / 子协议
  → 目标信息、uid 状态、上游状态码、响应体预览
  → 建议：补 x-mock-host、注册客户端、信任证书、检查子协议、改用 HTTP/1.1
  → 复制诊断信息
```

## 7. 与现有能力的协同

| 现有能力 | WebSocket 复用方式 | 产品注意事项 |
|---|---|---|
| 客户端注册与 uid | 完全复用；记录按 uid 路由到 viewer/device | uid 离线时仍转发但不展示，需要提示 |
| 客户端选择器 | 选择目标客户端查看/配置 | 列表是否跨客户端展示需明确（建议默认全部，支持筛选） |
| `dataServer` 环境切换 | `http(s)` 自动映射到 `ws(s)` | 设置页文案说明“同时作用于 HTTP 与 WS” |
| 设备延迟 | 只作用于握手与 Mock 消息 | 不逐帧延迟真实透传，避免破坏时序 |
| 启用 Mock 规则 | 同一规则同时覆盖 HTTP 与 WS | 规则管理需展示包含的协议与记录数 |
| 录制面板 | 连接详情新增“录制到规则” | 复用规则选择、去重、冲突、历史撤销心智 |
| 结构化编辑器 | HTTP 响应编辑器保持不变 | WS 使用独立脚本编辑器，避免塞进响应体 |
| 匹配引擎 | 增加协议维度，复用 host/path/query/header | 未命中诊断复用相似度模型 |
| 规则导入/导出 | 规则包增加 WS 记录与脚本 | 旧包导入兼容，`protocol` 缺省为 http |
| 接入向导/诊断中心 | 增加 WS 片段与握手诊断 | 错误码与 HTTP 统一风格 |
| 主题/i18n/滚动条 | 复用现有组件与规范 | 消息列表内部滚动，固定工具条 |
| 推送通道 | 复用 SockJS，批量推送 WS 消息 | 高频消息必须批处理，避免 UI 卡顿 |

## 8. 数据保留与性能的产品规则

### 8.1 保留

| 项 | 建议默认值 | 用户可见方式 |
|---|---|---|
| 列表连接数 | 40 条（与 HTTP 列表上限一致） | 淘汰提示、锁定保护 |
| 同时活跃连接 | 128 条 | 超出返回 503 并提示 |
| 每连接消息数 | 1000 条 | “仅保留最近 1000 条” |
| 单条消息 | 256KB | “已截断，原始 N KB” |
| 二进制消息 | 128KB（base64 后） | 提示复制/导出完整内容的限制 |
| 每连接总记录 | 4MB | 超出丢弃最旧消息 |
| 全局记录内存 | 64MB 量级 | 丢弃计数汇总提示 |

### 8.2 丢弃与截断

- 截断：保留原始大小、方向、类型、时间；内容末尾标记“已截断”。
- 丢弃：连接行显示“已丢弃 N 条”；详情顶部显示丢弃区间。
- 不允许静默丢弃；导出时明确标注哪些消息被截断/丢弃。

### 8.3 锁定与暂停

- 锁定：保护连接不被 40 条上限淘汰，最多 3 条。
- 暂停记录：停止采集与推送，保持转发；恢复后插入分隔标记。
- 清空：支持清空全部、清空当前连接消息；均需二次确认。

### 8.4 隐私与安全

- 观测模式只在内存中保存，不落盘；退出应用即清空。
- 沿用 HTTP 当前策略：不主动脱敏请求头；后续可增加“隐藏敏感字段”开关。
- WS 代理与 HTTP 一样是局域网开放中继，文档提示仅在可信研发网络使用。
- Mock、断开等控制动作必须显式启用/确认，不默认拦截。

## 9. 错误码与用户提示

| 错误码 | 场景 | 用户提示 | 建议动作 |
|---|---|---|---|
| WS-E01 | 缺少 `x-mock-host` / `__mock_host` | 未指定原始 WS 地址 | 检查拦截器或查询参数 |
| WS-E02 | uid 缺失/离线 | 客户端未注册，记录不会展示 | 重新扫码注册或检查 uid |
| WS-E03 | 目标协议不支持 | 只支持 ws/wss（由 http/https 映射） | 修改 `x-mock-host` |
| WS-E04 | DNS/TCP 失败 | 无法连接上游 | 检查网络、host、端口 |
| WS-E05 | TLS 失败 | 上游证书校验失败 | 使用有效证书或检查代理证书信任 |
| WS-E06 | 上游非 101 | 上游返回 401/403/500 | 展示状态码与响应体预览 |
| WS-E07 | 握手超时 | 上游握手超时 | 检查上游服务与网络 |
| WS-E08 | 子协议不匹配 | 上游未选择客户端提供的子协议 | 检查 `Sec-WebSocket-Protocol` |
| WS-E09 | 客户端非 HTTP/1.1 | 当前不支持 HTTP/2 扩展 CONNECT | 使用 HTTP/1.1 WebSocket 客户端 |
| WS-E10 | 连接数超限 | 同时连接过多 | 关闭闲置连接或调整上限 |
| WS-E11 | 消息过大 | 超过单帧上限 | 调整上限或使用二进制导出 |
| WS-E12 | 代理内部错误 | 连接被代理关闭 | 复制诊断信息反馈 |

所有错误都要在连接详情显示：目标、客户端、失败阶段、原始错误、可执行建议、复制按钮。

## 10. 埋点与验证

### 10.1 埋点（本地、匿名、可选）

| 事件 | 关键属性 |
|---|---|
| `ws_proxy_enabled` | 设置开关、协议 |
| `ws_connection_opened` | 客户端类型、目标 host、是否 query 接入 |
| `ws_connection_closed` | 关闭码、时长、帧数、是否 Mock |
| `ws_error` | 错误码、失败阶段 |
| `ws_detail_opened` | 连接来源（列表/向导/诊断） |
| `ws_frame_opened` | 方向、类型、大小区间 |
| `ws_frame_searched` | 是否有结果、筛选组合 |
| `ws_connection_locked` | 锁定/解锁 |
| `ws_recording_paused` | 暂停/恢复 |
| `ws_mock_created` | 拒绝/伪造/透传、是否来自录制 |
| `ws_mock_hit` | 规则、模式、消息数 |
| `ws_mock_miss` | 最相似规则、失败维度 |
| `ws_script_replayed` | 原时序/压缩时序、循环 |
| `ws_disconnect_injected` | 关闭码 |
| `ws_exported` | 连接/规则包 |

### 10.2 验证计划

1. **内部 Dogfood（1 周）**：用 2–3 个真实 App（IM/推送/订单）验证接入、消息形态与断线场景。
2. **小范围 Beta（2 周）**：10–20 名移动端开发/测试；观察首条连接耗时、消息详情打开率、错误码分布。
3. **Mock 专项验证（WS-2 后）**：让测试同学用脚本推送完成一次“后端未就绪”的联调；记录从创建到命中的耗时。
4. **性能压测**：20 条连接 × 50 帧/秒 × 1KB，持续 10 分钟；检查内存、UI 帧率、SockJS 延迟、丢弃提示。
5. **回归**：HTTP 代理、HTTP Mock、规则导入导出、接入向导、诊断中心全量回归。

## 12. 风险与待确认

### 12.1 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 用户期待“帧级抓包” | 认为消息列表不够专业 | UI 明确“消息级、分片已重组”；保留后续 raw 模式 |
| 压缩/101 附加头不保真 | 少数鉴权/压缩场景异常 | 文档说明；有强需求时做兼容模式 |
| Socket.IO/Protobuf 用户期待解码 | 看到的是原始文本/二进制，觉得难用 | 首版明确“传输层可见”；后续做协议插件 |
| 高频消息压垮 UI | 卡顿、内存增长 | 批量推送、上限、暂停记录、丢弃提示 |
| 长连接被淘汰 | 用户正在看的连接消失 | 锁定 + 选中保护 + 淘汰提示 |
| 重连风暴刷屏 | 列表噪音 | 重连聚合、按 URL 折叠 |
| Mock 复杂度膨胀 | 编辑器难用、规则冲突 | 模板化、协议维度隔离、命中诊断 |
| 开放中继被滥用 | 安全风险 | 与 HTTP 同风险；文档提示可信网络 |
| HTTP/2 客户端不兼容 | 连接失败 | 明确 HTTP/1.1 要求与错误提示 |

### 12.2 待确认问题

1. 首批用户主要使用 OkHttp、WebView/H5，还是 Socket.IO/STOMP？这决定向导与协议解码的优先级。
2. WS Mock 是否必须与 HTTP 共用“启用规则”？当前建议共用规则、记录分文档。
3. 是否需要“手动发送消息”进入 WS-2，而不是 WS-3？若测试同学强需求，可前移。
4. 默认保留上限（40 连接/1000 消息/256KB）是否符合真实调试深度？需要 Dogfood 校准。
5. 是否需要敏感字段脱敏（Authorization/Cookie/token）？若面向测试/外包团队，建议提前。
6. 是否需要在 WS-1 就提供“导出连接”，还是随 WS-3 的规则包一起做？
7. 上层协议解码（Socket.IO/STOMP）是否作为差异化重点，还是保持原始消息即可？
