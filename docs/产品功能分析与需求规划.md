## 1. 文档说明

### 1.1 目的

本文从产品经理视角评估 AppApiProxy 的现状，回答四个问题：

1. 当前产品解决了什么问题，目标用户是谁？
2. 与市面同类产品相比，优势和短板分别是什么？
3. 哪些需求最值得优先投入？
4. 未来 3–9 个月的产品路线应该怎么走？

### 1.2 方法

- **代码与文档走查**：基于当前仓库源码、使用说明文档、提交记录，核对功能是否真实可用。
- **竞品公开资料调研**：Charles、Proxyman、Fiddler Everywhere、Whistle、Reqable、HTTP Toolkit、Mockoon、WireMock、Apifox、Postman、Requestly、mitmproxy 等。
- **产品分析框架**：定位陈述、用户分层、JTBD、能力成熟度、竞品矩阵、RICE/价值-成本优先级、北极星指标。

### 1.3 局限性

- 未接入线上埋点，缺少真实留存、激活漏斗和命中率数据，部分判断基于代码与文档推断。
- 竞品功能与价格随版本变化，矩阵中的符号仅表示相对能力，具体以各产品官网为准。
- 未进行用户访谈，用户痛点排序需要在下一阶段验证。

## 2. 结论摘要

### 2.1 现状判断

AppApiProxy 的核心闭环「接入 → 抓包 → 录制 → Mock → 切回真实」已经跑通，工程完成度不低：

- HTTP/2 与 HTTP/1.1 兼容；
- gzip/deflate/br/zstd 解码展示；
- 多设备 UID 隔离与归属模型；
- PouchDB 本地持久化与旧数据迁移；
- 自动更新、托盘、单实例、i18n、主题。

但产品仍停留在「个人调试工具」阶段，距离「团队级 Mock 工作台」有明显差距。

### 2.2 最大问题

最大问题不是功能数量，而是 Mock 的「可命中、可编辑、可复用」不足：

| 问题 | 影响 |
|---|---|
| 只按 URL 精确匹配，不区分 Method/Host | GET/POST 同路径互相覆盖，多 Host 冲突 |
| Query 顺序、动态签名、时间戳影响匹配 | 真实 App 录制规则大面积不命中 |
| 响应是静态快照 | 无法生成动态数据、边界数据、序列场景 |
| 编辑方式是整段 JSON | 测试/产品同学门槛高，效率低 |
| 请求记录只在内存保留 40 条 | 重启即丢，无法承担「回归样本库」 |
| 未命中时无解释 | 用户只能猜为什么规则没生效 |

### 2.3 市场判断

- 抓包侧：Charles、Proxyman、Fiddler、Whistle、Reqable、HTTP Toolkit，竞争充分。
- Mock 侧：Mockoon、WireMock、Apifox、Postman，能力成熟。
- 中间位置：「真实移动流量 → 可编程场景 → 可分发的团队资产」仍有空档。
- **Reqable 是最接近、也最危险的竞品**：已覆盖抓包、调试、Mock、脚本、移动端协同和 MCP。

### 2.4 战略建议

不要做「又一个 Charles」，也不要做「又一个 Mockoon」。建议把定位收窄为：

> **面向移动端/多端联调的「流量驱动 Mock 工作台」：扫码接入、无需 root/系统代理；把一次真实请求变成可编辑、可复用、可分发的 Mock 场景。**

执行顺序：

1. 先补地基：匹配引擎、结构化编辑、持久化；
2. 再做场景：断点/改写、条件/序列/状态机；
3. 最后做平台与智能化：契约校验、MCP/AI、CLI/CI、团队规则库。

## 3. 产品现状评估

### 3.1 定位与目标用户

**当前隐含定位：** 前后端并行开发的本地调试代理 + 数据 Mock 工具。

**建议明确定位：** 移动端真机联调的流量驱动 Mock 工作台。

**目标用户分层：**

| 层级 | 用户 | 核心诉求 | 当前匹配度 |
|---|---|---|---|
| 核心 | 移动端开发（Android/iOS/鸿蒙） | 真机抓包不改系统代理；后端没好时继续开发 | 高 |
| 核心 | PC 客户端 / H5 / 小程序开发 | 查看请求、构造边界数据 | 中高 |
| 扩展 | 测试工程师 | 异常态、弱网、边界数据验证 | 中 |
| 扩展 | 小型研发团队 | 共享 Mock 样本、多人多设备联调 | 低 |
| 非目标 | 安全研究、通用 Web 抓包、大型 API 平台用户 | 系统级抓包、契约管理、服务虚拟化 | 低 |

**建议的价值主张：**

- 对移动端开发者：不用 root、不用装证书、不用改系统代理，扫码即可抓真机流量。
- 对并行开发：一次真实请求，三秒变成可编辑、可复用的 Mock 场景。
- 对团队：Mock 数据留在本地，规则可导出、可分享、可进 Git。

**定位陈述：**

> 面向移动端/多端联调的本地流量 Mock 工作台。
> 它不要求 root、不要求系统代理，扫码即可接入真机；
> 把一次真实请求变成可编辑、可复用、可分发的 Mock 场景；
> 与通用抓包工具相比，它更懂「场景沉淀」；与契约 Mock 平台相比，它更贴近「真实流量」。

### 3.2 能力盘点

> 成熟度为产品经理主观评分，用于相对比较，不代表工程质量结论。

| 能力域 | 已具备 | 成熟度 | 关键缺口 |
|---|---|---|---|
| 接入 / 代理 | `/_proxy` + `x-mock-host` / `x-mock-uid`；HTTP/2 与 HTTP/1.1；HTTPS 自签名；二维码设备注册；按 UID 隔离 | ★★★★☆ | 需改代码；证书处理有门槛；无系统代理模式；重定向/Cookie 有限制 |
| 流量观测 | 实时列表、请求/响应详情、格式化/折叠/搜索、媒体预览、Mock 标记、耗时 | ★★★☆☆ | 仅内存 40 条；无持久会话、多维筛选、响应对比；WebSocket/gRPC 未抓；单条 1MB 截断 |
| 转发 | 全方法、二进制、multipart、chunked、Range；15s 超时；gzip/br/zstd 解码展示 | ★★★★☆ | 无请求/响应改写、断点；Map Remote 未产品化；上游仅 HTTP/1.1 |
| Mock | 录制→规则、按 UID 开关、规则/记录分文档存储、分页加载 | ★★☆☆☆ | 匹配刚性；静态响应；无模板/变体/场景；编辑原始 JSON |
| 场景控制 | 每 UID 固定延迟；手工改状态码/响应体 | ★★☆☆☆ | 无条件、序列、概率、错误注入；无弱网模板 |
| 数据 / 协作 | PouchDB 本地持久化；配置本地文件；旧数据自动迁移 | ★★☆☆☆ | 无会话持久化；无导入导出/分享；无团队、版本、契约 |
| 工程化 | 增量/全量更新、托盘、单实例、i18n、主题 | ★★★★☆ | 无 CLI/CI、插件/脚本、MCP/AI；存在占位功能 |

### 3.3 核心闭环与体验断点

当前用户旅程：

1. 设置代理 IP / 端口 / 协议；
2. 被测 App 改 URL + 两个 Header；
3. 扫码让设备注册，拿到 UID；
4. 发请求，桌面端实时看到记录；
5. 点书签把请求带入规则，编辑响应，打开开关；
6. 后续请求命中 Mock，停止后端也能开发。

**闭环跑得通，但断点集中在后半段：**

| 阶段 | 断点 | 用户感受 |
|---|---|---|
| 接入 | 必须改代码；HTTPS 证书要单独处理；二维码/UID 概念不直观 | 「第一步就卡住」 |
| 命中 | Query 带时间戳、签名、设备 ID、版本号，精确匹配易失效 | 「录了但用不上」 |
| 编辑 | 整段 JSON 手改，状态码/响应头/响应体混在一起 | 「只有开发能用」 |
| 沉淀 | 记录不落盘、不能搜历史、不能导出分享 | 「只能当临时工具」 |
| 解释 | 未命中时不知道为什么 | 「只能猜」 |

### 3.4 优势

1. **零 root、零系统代理的设备接入。** 相对 Charles/Proxyman 最锋利的差异点，适合移动端和受管控设备。
2. **录制到 Mock 的最短路径。** 比 Mockoon/WireMock 手工建接口更贴近真实流量。
3. **多设备归属模型。** viewer + device + ownerUid，记录、延迟、Mock 天然隔离，适合多端联调。
4. **本地优先。** 数据不上云，适合有隐私要求的团队。
5. **媒体预览。** 图片/音频/视频/HLS 预览是很多抓包工具没有的细节，对内容型 App 有价值。
6. **工程化基础不错。** 自动更新、托盘、单实例、主题、中英文，具备持续交付能力。

### 3.5 关键短板

#### P0 级（直接影响核心价值）

1. **匹配引擎太弱。**
   - 只按 URL 精确匹配，不区分 Host 和 Method；
   - 记录 key 仅 `url`，GET/POST 同路径会互相覆盖；
   - Query 顺序、大小写、动态签名都会导致不命中；
   - 未命中时没有诊断信息。

2. **请求记录不持久。**
   - 只保留最近 40 条，且只在内存；
   - 重启即清空，无法回看历史问题；
   - 与「回归数据沉淀」的产品叙事冲突。

3. **响应编辑太原始。**
   - 解析整段 JSON，状态码/响应头/响应体没有结构化表单；
   - 没有模板变量、响应变体、字段级校验；
   - 测试同学和产品同学基本无法参与。

4. **大响应展示受限。**
   - 单条记录展示截断到 1MB；
   - 列表、详情、媒体元数据类接口可能看不全。

#### P1 级（影响效率与深度）

5. **场景能力弱。** 只有固定延迟；没有条件响应、序列响应、概率失败、错误注入、弱网模板。
6. **无断点/改写。** 不能在请求发出前或响应返回前修改，不能做 Header 重写、状态码替换、Map Local/Map Remote。
7. **无重放/对比。** 不能一键重发、编辑后重发、对比两次响应。
8. **无导出/分享。** 规则只能留在本机 PouchDB，不能导出 JSON/HAR，不能进 Git。
9. **无契约能力。** 不支持 OpenAPI 导入、响应 Schema 校验、字段缺失检测；「API 定义服务地址」仍是占位配置。
10. **协议覆盖不足。** WebSocket 只有筛选图标没有帧抓取；gRPC/GraphQL 未支持；SSE 只用于内部推送。

#### 产品债与半成品

- 设置里的 `apiDefineServer`、`statRuleServer`、`dataServer` 没有真正打通；`dataServer` 在后端有 Map Remote 能力，但 UI 只暴露延迟配置。
- `/upload` 路由指向并不存在的 `mockService.upload`。
- 静态资源管理只有一个没有绑定逻辑的上传控件。
- 打点、WebSocket 类型保留但未启用，容易让用户误以为已支持。

### 3.6 阶段判断

这是一个**功能可用的 MVP+ / 早期工具型产品**：

- 核心链路完整，细节体验有亮点；
- 但缺少留存、命中率、激活漏斗等数据，PMF 尚未被验证；
- 当前更像「作者自己用得顺手的工具」，还不是「团队愿意持续使用的产品」。

**建议先补三类数据：**

1. 激活漏斗：安装 → 首个请求 → 首个 Mock 命中；
2. 周活跃与次周留存；
3. Mock 命中率与未命中原因分布。

没有这些数据，后续优先级只能靠猜。

### 4.3 重点竞品点评

#### Charles

抓包/改写/Map Local 的行业基准，能力全面、稳定；但 UI 老旧、无团队协作、无 AI。它的「保存响应 + Map Local」是静态文件式 Mock，不适合动态数据。

**对我们的启示：** 断点、Rewrite、Map Local/Remote 是用户已经形成肌肉记忆的能力，缺失会直接导致「不如 Charles」的评价。

#### Proxyman

原生体验最好，macOS/iOS 生态强；断点、Map Local、JS 脚本、MCP 都在做。它代表了「抓包工具正在变成 AI 可调用的调试平台」这一趋势。

**对我们的启示：** 体验和 AI 可调用性是下一阶段的竞争点；但 Proxyman 不解决「团队 Mock 资产」问题。

#### Fiddler Everywhere

企业友好，Auto Responder + Rules + 团队工作区，Mock 能力比 Charles 更产品化；但偏重、订阅制。

**对我们的启示：** Auto Responder 的「按规则返回响应」是 Mock 产品的标准交互，我们需要在保持录制优势的同时补齐规则能力。

#### Whistle

免费、规则引擎强、插件生态好，国内前端渗透率高；但 CLI/Web UI 形态、学习曲线陡，Mock 以规则文本为主。

**对我们的启示：** 规则表达能力是刚需；但纯文本规则对测试/产品不友好，结构化 UI 是差异化机会。

#### Reqable

**最直接竞品。** 抓包 + 调试 + 测试 + Mock + 脚本 + 移动端协同 + MCP，免费版可用，专业版价格低（约 ¥99/年）。它在「抓包工具一体化」上走得最远。

**对我们的启示：**

- 不要在同一维度拼功能数量；
- 我们的机会是「更聚焦移动端联调 + 更懂场景沉淀 + 更轻的接入」；
- 需要密切关注它的 Mock、脚本和 MCP 迭代。

#### HTTP Toolkit

零配置拦截浏览器/Android/Node/Docker 做得最好，开源；但 Mock/场景能力偏轻，偏工程化。

**对我们的启示：** 「零配置」是强需求；我们的「代码级接入 + 扫码」是另一种零配置路径，需要把接入体验做到同样顺滑。

#### Mockoon

纯 Mock 的体验标杆，Faker 模板、规则、代理模式、CLI、Cloud/团队都成熟；但需要自己建接口，不贴近真实 App 流量。

**对我们的启示：** 模板、规则、CLI、团队是 Mock 产品的完整拼图；我们不需要全做，但模板和规则必须补。

#### WireMock

服务虚拟化/契约测试的工业标准，录制回放、状态场景、CI 集成强；重，适合后端/测试平台。

**对我们的启示：** 状态场景（Scenarios）和录制回放是高级 Mock 的方向，可作为中期目标。

#### Apifox / Postman

契约驱动的一体化平台，Mock 只是模块；团队、文档、测试、AI 都强。它们会吃掉「团队级 Mock 平台」的市场，正面竞争没有胜算。

**对我们的启示：** 不做文档/测试/团队权限平台；做它们不擅长的「真实流量侧」。

#### mitmproxy

可编程代理的极客工具，脚本能力强；无产品化 GUI，适合工程师而不是团队。

**对我们的启示：** 脚本能力可以作为后期插件化方向，但不应成为早期重点。

### 4.4 趋势判断

1. **抓包、调试、测试一体化。** Reqable 已经把三者做成一个产品；单点抓包工具的价值在下降。
2. **Mock 从「静态回放」走向「可编程、有状态」。** Mockoon 的数据桶、WireMock 的 Scenarios 都是信号；只会返回固定 JSON 的 Mock 会越来越不够用。
3. **契约驱动与流量驱动在融合。** 录制真实流量生成接口/样例，再用 OpenAPI 校验，是自然的下一步。
4. **AI/MCP 成为新入口。** Proxyman 已提供 MCP（约 27 个工具，让 AI 代理读取流量、重放请求、控制断点），Reqable 3.2 支持 MCP，Whistle 有社区 MCP，Postman 有 Agent Mode。2026 年之后，「AI 能不能操作你的调试工具」会变成基础能力。
5. **本地优先与团队协作并行。** 隐私敏感团队要本地；团队又要共享规则。文件化、Git 化是低成本折中。
6. **移动端多设备协同。** 真机 + 模拟器 + 多端并行是移动团队的日常，按设备隔离记录/配置是刚需。

### 4.5 定位图与机会窗口

用两个维度看：

- **横轴：真实流量驱动程度**（从「手工建接口」到「完全由真实流量产生」）
- **纵轴：Mock 可编程/场景化程度**（从「静态回放」到「模板、脚本、状态机」）

当前格局：

| 象限 | 产品 | 特征 |
|---|---|---|
| 左上：流量强、Mock 中低 | AppApiProxy、Charles、Fiddler | 贴近真实流量，但 Mock 偏静态/规则 |
| 右上：流量强、Mock 强 | Proxyman、Whistle、Reqable、HTTP Toolkit | 抓包 + 脚本/规则，综合能力强 |
| 右下：流量弱、Mock 强 | Mockoon、WireMock、Apifox、Postman | 契约/规则驱动，不依赖真实流量 |

AppApiProxy 当前处于「左上」，价值最容易流失。需要向右上移动：保留「真实流量 + 移动真机 + 零 root」的优势，同时提升 Mock 的可编程性。

**机会窗口：**

> **真实移动流量 + 零 root 接入 + 可编程场景 + 可分享的规则包。**

这个位置目前只有 Reqable 部分覆盖，而 Reqable 的重心是「抓包 + 调试 + 测试」，不是「团队 Mock 资产」。AppApiProxy 应该避开正面功能竞赛，用「移动端真机 + 录制式场景库」建立差异。

### 5.3 Now / Next / Later 路线图

#### Now（0–6 周）：让 Mock 真正命中

**目标：把「录了却用不上」变成「录了就能用」。**

##### 1）匹配引擎 v2（最高优先）

- 匹配维度：Method + Host（可选）+ Path（精确/通配/正则）+ Query（必填/忽略/顺序无关）+ Header 条件；
- 动态参数识别：自动提示 timestamp/sign/nonce/deviceId 等易变参数，支持一键加入忽略列表；
- 优先级与回退：多规则按优先级匹配，未命中时回退真实代理；
- 命中解释：显示「命中了哪条规则」；未命中时显示「最接近的规则 + 差异原因」；
- 数据模型：记录 key 从 `url` 升级为 `method + host + path + query` 的可配置指纹。

**验收标准：** 在 3 个真实 App 上，录制规则无需手改 URL 的命中率 ≥ 80%；未命中原因可解释。

##### 2）结构化响应编辑器

- 状态码、响应头、响应体分栏编辑；
- 模板变量：时间、随机数、UUID、Faker 常用字段、序列值；
- 响应变体：同一请求保存「正常/空态/错误/边界」多个变体，快速切换；
- 单条规则可设置延迟、错误码、超时、断连。

**验收标准：** 新建一条规则并生成 3 个边界变体 ≤ 3 分钟，无需手写完整 JSON。

##### 3）接入向导 + 自检

- OkHttp/Retrofit、axios/fetch、Flutter dio、iOS URLSession、Python requests 的可复制片段；
- 设备连通性自检：设备 → 代理 → 上游 → Mock 四段链路逐段提示；
- 二维码流程简化，明确「当前 UID / 归属桌面端 / 是否在线」。

**验收标准：** 新用户不看文档 10 分钟内完成首个代理请求。

##### 4）规则导入/导出

- JSON 规则包导出/导入，HAR 导入生成记录；
- 导出内容包含规则元信息、记录、变体，可进 Git。

**验收标准：** 导出到另一台机器导入后，Mock 行为一致。

##### Now 交付状态回填（2026-11-10）

| Now 项 | 实际状态 | 说明 |
|---|---|---|
| 1）匹配引擎 v2 | 已交付（schema v4） | 迁移复核与撤销的**后端与接口已完成、渲染层未接入**，验收路径缺最后一环 |
| 2）结构化响应编辑器 | 部分交付 | 结构化编辑 + 变体 + 原始 JSON 已交付；**模板变量与预览未实现**，`{{...}}` 按原文返回 |
| 3）接入向导 + 自检 | 已交付 | 向导四步、健康检查、链路诊断、代码片段可用 |
| 4）规则导入/导出 + HAR | **未交付** | 代码中无导入导出与 HAR 任何实现，O4「让规则可流转」顺延到下一版本 |
| — WebSocket 观测 | **交付范围外新增** | 原列 Later，因主界面已挂 WS 筛选图标、说明文档已承诺「不解析帧」形成产品债而提前 |
| — 应用更新链路 | **交付范围外新增** | 全量/增量区分、asar 占用、Windows 权限与 UAC 取消回滚，两次修正才稳定 |

> 未回填的差异分析、成因归类与撰写检查清单见 [PRD v1.1 第 13 节](./PRD-v1.1-0-6周需求.md#13-需求演进复盘与初版盲区)。

#### Next（6–16 周）：让流量成为可检索、可复用的资产

##### 5）会话持久化与检索

- 请求记录落盘（PouchDB/SQLite），按会话/时间/设备保存；
- 多维筛选：Host、Method、状态码、是否 Mock、耗时、关键字；
- 固定/对比/批量删除；HAR 导出。

**验收标准：** 重启后可查 7 天前请求；导出 HAR 能被 Charles 打开。

##### 6）重放 / Composer / 响应对比

- 一键重发到代理或原始服务；编辑 Method/URL/Header/Body；
- cURL 导入/导出；
- 两次响应 diff（JSON 结构化对比）。

**验收标准：** 复现线上问题请求 ≤ 2 次点击；diff 能定位字段级变化。

##### 7）断点 / 改写 / 环境切换

- 请求前、响应后断点，可修改后放行；
- Header/状态码/响应体改写，Map Local/Map Remote；
- 把 `dataServer` 真正产品化：开发/测试/预发/生产环境一键切换。

**验收标准：** 不写代码即可把线上接口指向测试环境，并修改一个 Header。

##### 8）场景 / 状态机 Mock

- 条件响应：按 Query/Header/Body/设备返回不同响应；
- 序列响应：第 1 次 401、第 2 次 200；轮询/递增；
- 概率与错误注入：按比例返回 500/超时/空数据；
- 弱网模板：慢 3G、断网、抖动。

**验收标准：** 不写脚本即可模拟「登录过期 → 刷新 → 成功」的完整流程。

#### Later（4–9 个月）：平台化与智能化

##### 9）OpenAPI 契约导入与校验

- 从 OpenAPI/Swagger 生成初始规则和响应模板；
- 用 Schema 校验真实响应，标记缺字段/类型错误；
- 把「接口文档」与「录制样本」关联起来。

##### 10）WebSocket / SSE 抓取与 Mock

- 帧列表、消息详情、按连接隔离；
- 支持服务端推送模拟（消息序列、定时推送）。

##### 11）MCP / AI 助手

- MCP Server：让 AI Agent 查询流量、搜索请求、创建/切换规则、重放、解释未命中；
- 自然语言生成规则：「把这个接口的空列表和 500 错误各做一个变体」；
- 本地优先、默认脱敏、显式授权、支持自带模型 Key。

> 这是中期差异化重点，但不应早于匹配/编辑/持久化。匹配和编辑做不好，AI 只会更快地产生错误的 Mock。

##### 12）CLI / CI

- 从规则包启动无头 Mock Server；Docker 镜像；
- GitHub Action：前端构建时用 Mock 规则跑契约测试。

##### 13）团队规则库

- 规则包版本化、评论、变更 diff；
- 先做文件/Git 共享，再做云端空间，避免过早背上协作复杂度。

### 5.4 版本节奏建议

| 版本 | 主题 | 内容 | 预计 |
|---|---|---|---|
| v1.1 | 命中 | 匹配 v2、结构化编辑器、接入向导、导入导出 | 4–6 周 |
| v1.2 | 沉淀 | 会话持久化/检索、HAR、重放/对比 | 6–8 周 |
| v1.5 | 场景 | 断点/改写、环境切换、场景/状态机、WS 抓取 | 8–10 周 |
| v2.0 | 平台 | OpenAPI 校验、MCP/AI、CLI/CI、团队规则库 | 下一阶段 |

> 如果是单人/小团队维护，建议每个版本只押 1 个主题，避免并行铺开导致每个功能都半成品。

### 5.5 信息架构建议

当前「Mock 规则」这个概念同时承担了「场景集合」和「匹配规则」两个职责，后续做场景化会越来越别扭。建议：

| 概念 | 定义 | 对应现状 |
|---|---|---|
| 场景（Scenario） | 一组请求响应的集合 | 现在的「规则」 |
| 规则（Rule） | 场景内的匹配条件（Method/Host/Path/Query） | 目前隐含在 URL 中 |
| 变体（Variant） | 同一请求的不同响应 | 目前不存在 |
| 设备（Device） | 绑定某个场景/环境 | 目前只能继承桌面端 |

术语调整越早越好，否则后续数据模型和 UI 都会背上历史包袱。

### 5.6 风险与不做清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 中间地带被两端挤压 | 高 | 聚焦「移动真机 + 流量驱动场景库」，不与 Charles/Reqable 比抓包广度，不与 Apifox 比平台 |
| 匹配不中导致价值不成立 | 高 | 匹配 v2 作为第一优先；命中诊断必须做 |
| 范围蔓延 | 中高 | 明确「不做」清单；每季度只押一个差异化主题 |
| 协议广度陷阱 | 中 | HTTP/WS 优先，gRPC/HTTP3 后置 |
| AI/隐私 | 中 | 本地优先、默认脱敏、显式授权、可关闭 |
| 单人维护成本 | 中高 | 补齐代理边界测试；清理占位功能，降低认知与维护负担 |

**明确不做（至少现在不做）：**

- 不做通用系统级抓包，不与 Charles/Reqable 正面竞争；
- 不做完整 API 文档/测试管理平台，不与 Apifox/Postman 正面竞争；
- 不做大规模云端 Mock/服务虚拟化，不与 WireMock 正面竞争；
- 不追求全协议覆盖（gRPC/HTTP3/MQTT）优先；
- 不做重型团队权限/审计，除非 PMF 已验证。

**建议清理的产品债：**

- 要么实现、要么隐藏：WebSocket 筛选、打点类型、静态资源上传、`/upload` 路由；
- 把 `apiDefineServer`、`statRuleServer` 从设置里移除或标注「即将支持」；
- 把 `dataServer` 从占位配置变成真正的环境切换功能。

> **2026-11-10 对账**：WebSocket 筛选已按「实现」清偿；**打点类型、静态资源上传仍是占位**（说明文档第 10 节已标注「打点数据通道未启用」「静态资源管理为占位功能」）。本清单的价值在于它预测了 v1.1 最大的范围变化——**只要半实现的入口继续留在 UI 上，它迟早会变成范围外需求**。后续每个版本立项前先跑一遍这份「已承诺未实现」清单。

### 5.7 验证计划

1. **用户访谈（1–2 周）**
   - 找 8–10 名移动端开发/测试；
   - 观察他们现在如何解决「后端没好/真机抓包/异常构造」；
   - 重点验证匹配和持久化是不是第一痛点。

2. **技术 Spike（2 周）**
   - 用 3 个真实 App 验证匹配 v2 的命中率，目标 ≥ 80%；
   - 如果达不到，说明定位需要调整。

3. **小范围 Beta（4 周）**
   - 20–30 名用户；
   - 埋点（可选、匿名、本地）观察激活漏斗、TTFM、周 Mock 命中、次周留存。

4. **商业化验证（可选）**
   - 参考 Reqable 约 ¥99/年、Proxyman $89 买断 / $12/年、Mockoon €10/用户/月、Apifox ¥182+/年；
   - 测试「个人 Pro / 团队版」的接受度。

## 6. 决策建议

1. **当前产品已经「能用」，但还没「好用」到能沉淀用户。** 第一优先级不是加功能，而是把 Mock 命中率从「看运气」提升到「可预期」。
2. **不要试图成为 Charles 或 Mockoon。** 把「移动端真机 + 真实流量 + 可编辑场景 + 可分享规则」做成一个别人不愿意做的窄而深的位置。
3. **AI/MCP 是 2026 年的必答题，但不是第一题。** 匹配、编辑、持久化做不好，AI 只会让错误的 Mock 更快地产生。
