## 1. 结论摘要

1. **导出可以很快，导入必须慢。** 导出是「读 + 序列化 + 落盘」，风险集中在内存峰值与脱敏遗漏；导入是「读文件 + 校验 + 写库 + 缓存失效」，风险集中在**绕过既有写入管线**。本设计把 70% 的工程量放在导入侧的写入正确性上。
2. **PRD 4.4.6「导入写入使用 PouchDB `bulkDocs`」必须推翻。** 现有 `saveRecord()` 是唯一写入路径，内部承担 normalize → 指纹 → 查重 → 迁移闸门 → 落盘 → 变更通知六件事；`bulkSave()` 是裸 `bulkDocs`，**六件事全部跳过**。直接用它导入会产生「导入成功但规则不生效且无任何报错」——最难排查的一类故障。详见 [6.2](#62-写入必须复用单条保存管线推翻-prd-446)。
3. **文件读写链路是真正的前置阻塞项，且不能按 PRD 现状假设。** `selectFile` 过滤器只允许图片且只返回路径不返回内容；`saveFile` 无返回值、取消与失败都被吞掉。两者**渲染层零调用方**——从未被真实走过，不能当作可用基建。见 [4](#4-关键决策)。
4. **导入会静默改变命中顺序，PRD 与评审都没提。** `saveRecord()` 对新建记录强制 `createdAt = updatedAt = now`，而 R1 的排序兜底是 `updatedAt` 降序。按现有管线导入一批记录，会把原机器上的优先级顺序打乱。必须让导入路径可注入时间戳，且**按模式取值（Q3 已裁决）**：新建与复制取包内原值，合并覆盖取库内已有值——后者因此要先读出现有 doc。AC-R4-01 的往返一致性也只在新建模式成立。见 [6.4](#64-时间戳与命中顺序必须可注入)。
5. **规则包与 HAR 都只做「拒绝」，不做「静默降级」。** 版本过高、条数超限、含 Body 条件、非法 JSON——一律整包或单条明确失败并给出原因；这与 `match.body` 已确立的拒绝语义一致。
6. **估算口径**：按文件级拆解为 **27.5 人日**（研发）+ QA 2.5，对 [评审文档 5.8 节的 8.5 人日](./PRD-v1.1-研发评审与任务拆分.md) 是 **+19**。差额可逐项追溯，见任务拆分第 7.1 节。

## 3. 目标与非目标

### 3.1 目标

- G1 规则包导出/导入闭环：记录、匹配、变体、当前变体、时间戳语义在跨机后与源机器一致（AC-R4-01）。
- G2 默认脱敏且不可遗漏：任何导出路径（桌面/Web、单场景/全场景）都走同一份脱敏实现（AC-R4-02）。
- G3 导入不破坏运行时一致性：指纹、查重、迁移闸门、缓存失效与单条保存完全等价。
- G4 HAR 导入生成可用记录，而不是「能导入但命中率归零」的记录（AC-R4-06/07/08）。
- G5 失败可解释：包级 / 条目级 / 冲突级三类失败各有码与明细。

### 3.2 非目标

- 不做规则包的增量同步、双向 merge、Git 冲突解决——只保证「导出即用」。
- 不做跨机导入时的启用状态迁移（导入后一律不自动启用）。
- 不做 HAR 的请求体匹配（延续 `match.body` 拒绝语义）。
- 不做加密导出、口令保护、云端中转。
- 不改动库内 schema 版本，不新增迁移步骤。

## 4. 关键决策

### D1 文件读取：渲染层 `<input type=file>` + multipart 上传，不用 `selectFile`

| 备选 | 判断 |
|---|---|
| A. 复用 `window.mainApi.selectFile()` | **否决**：过滤器只允许图片（`ipc-handlers.ts:64-69`），且返回路径不返回内容，渲染层无 fs 权限读不到文件。改造它等于同时改掉现有图片选择的行为。 |
| B. 新增 IPC `readFile` 返回内容 | **否决**：为本地工具开一条「任意路径读取」通道，安全面扩大；Web 端不可用，还得再写一套。 |
| **C. `<input type="file">` + `FormData` multipart POST**（选） | 桌面与 Web **同一份代码**；框架已有 multipart 解析（`base.router.ts:66-67`）；`limit: 50mb` 已就位（`MainServer.ts:174-176`）；文件二进制不进 JSON 转义链路，避免 50MB 字符串膨胀 3～5 倍。 |

**选 C 必须同时修两处**，否则上线即故障：

1. **mimetype 判定不可靠**：`fetchFormFile` 只在 `application/json` 时 `JSON.parse`，其它 mimetype 返回 `undefined`；而 `.har` 的 mimetype 由操作系统 MIME 表决定，浏览器可能给出 `application/json`、`application/octet-stream` 或空串。返回 `undefined` 会命中 `base.router.ts:94-98` 变成 `FAIL: biz inner error, no result found`，用户看到的是内部错误而不是「格式不对」。
   → 新增显式意图而非猜测：为 R4 端点引入 `ParamType.FormFileText`（取文件 utf-8 文本，由服务端统一 `JSON.parse` 并按 `format` 字段分派），或让 `fetchFormFile` 接受期望类型参数。**不新增第二套上传实现。**
2. **临时文件泄漏**：`formidable@3.5.4` 的上传文件落在临时目录，现有 `parse()` 后无任何清理（`base.router.ts:67`）。R4 把单次上传体积抬到 50MB 级，泄漏从理论问题变成磁盘问题。
   → 解析完成后必须 `consume()`/删除临时文件，且异常路径（校验失败、取消）也要清；同时显式设 `maxFileSize = 50MB`、限制文件数字段数，不依赖库默认值。

**落地状态（导入通道，2026-11-19；R4C-27 的前半）**：按 C 实现，选择器落在 `src/renderer/common/pack-file.ts` 的 `pickPackFile(kind)`——**两种部署形态同一份代码，不判 `window.isWeb`**（Electron 里点 `<input type="file">` 弹的就是系统原生选择框，桌面体验不比 `selectFile` 差，而 A/B 两案各自都要再为 Web 写一套）。白名单按 kind 单源在 `MOCK_PACK_FILE_ACCEPT`（`src/shared/mock.pack.ts`），扩展名与 mimetype 都给：`.har` 在多数系统里没有登记 MIME，浏览器给出的 `File.type` 常是空串，**主力是扩展名那一半**，mimetype 只服务只认类型的系统对话框；上传时 part 的类型由 `proxy.api.withFallbackMimeType` 补 `application/octet-stream`，服务端才把它当文件而不是普通字段。三处口径记在代码注释里：交出去的是 `File` 句柄（不转字符串、不重新包 Blob，否则 50MB 同时躺在 JS 堆与 axios 缓冲里）、体积超过 50MB 在**本机**就拦下并给 `mock.pack.packTooLarge`（multipart 硬上限只多 1MB 余量，越过它拿到的是断掉的请求而不是这句人话）、取消靠 `cancel` 事件（Chromium 107+；不接则 Promise 悬着、调用方 loading 转不停）。
本批只交付通道：**渲染层还没有调用方**（导入弹窗是 R4C-27），所以 `dist/web` 产物里暂时搜不到它——这是「代码写了但用户触发不到」的下一种形态，靠 `test/unit/pack-file.test.ts` 把契约钉住：白名单键集必须等于 `MOCK_PACK_KINDS`（新增 kind 忘了配白名单立刻变红）、闸门边界（恰好 50MB 放行、超 1 字节拦下且只弹一次）、以及选择器交出的 File 经真实 `importHar` 到真实路由后**文本逐字符原样**（非 ASCII + CRLF + emoji，`File.type` 空串与带 mimetype 两种各测一次，证明格式分派不看 mimetype）。

### D2 文件写出：主进程组装 + 主进程弹框落盘，返回值三态

| 备选 | 判断 |
|---|---|
| A. 主进程组装 → 返回 pack 文本 → 渲染层交 `saveFile()` | **否决**：50MB 文本要走 HTTP JSON envelope → axios → IPC structured clone，至少三次全量复制；且 `saveFile` 拿不到结果。 |
| **B. 主进程组装 + 保存对话框 + 写盘，只回传结果**（选） | 一次组装、零跨进程搬运；桌面端天然是主进程的事。 |
| C. Web 端 | 走 `GET exportMockPack` 拿文本后 Blob + `a.download`（`window.isWeb` 分支，`App.vue:66`）。Web 是本地/自建部署场景，体积风险由用户自担，UI 上提示建议改用桌面端。 |

**B 方案的生效条件（2026-11-19 基准补正）**：真正省内存的不是「走 IPC」，而是「主进程边拼边写、不把整包交还调用方」。R4C-06 落地时只做到了前半句——组装仍在主进程、但出口仍返回字符串，实测 42.7MB 包收尾活堆 +85.5MB（见 [6.3](#63-导出组装)，与「聚合成对象再 stringify」同档），跨进程克隆只是在此之上再叠一份。因此 B 必须含「写盘」这一半：只把弹框挪到主进程而仍返回文本，等于没解决问题。

**并修正 `saveFile` 语义**：当前 `canceled` 直接 return、写失败只 `console.log`、handler 无返回值、`MainApi.saveFile` 声明 `void` 且不 await（`ipc-handlers.ts:119-122`、`MainApi.ts:24`）。导出必须能区分 **saved / canceled / failed**，否则「导出成功」的提示是假的。返回 `{status, filePath?, error?}`，接口签名改 async。因渲染层零调用方，此改造**无回归面**——但也意味着它从未被真实验证过，须列入打包后冒烟项。

**落地状态（R4C-08，2026-11-19）**：B 方案按两段实现——`MAIN_API_CMD.SelectSavePath` 只弹保存框，返回 `{status: 'selected' | 'canceled', filePath?}`；`ExportMockPack(filePath, options)` 在主进程边拼边写，返回 `SaveMockPackResult`（`saved` 附 `filePath` / `ruleCount` / `recordCount`，`failed` 附 `error`），整包文本不再跨进程。保存框的标题、默认目录与过滤器抽到 `src/main/misc/save-path.ts`，`SaveFileAs` 与新通道共用一处定义。上一段「从未被真实验证过」对本批**仍然成立**：桌面端打包被环境挡住（`app.asar` 句柄占用），只跑了 `tsc` / 单测 / `build:web` / 离线 harness，保存框与写盘路径未真机点过，冒烟项不撤销。

### D3 写入：复用 `saveRecord` 的管线语义，禁止裸 `bulkDocs`

>
> 三条边界按实现定稿：① **ID 与时刻由调用方给**。`rec_<uuid>` 怎么分配、`createdAt` 是否沿用包里的值（R4C-16）、复制为新记录（R4C-18）——这些是不同路径各自的决定，写进组装函数就是把同一个决定做两次；副作用是 `Date.now()` 留在 `saveRecord` 里，注入点因此只剩一处。② `existing` 用 `null` 表示新建分支，`_rev`/`createdAt`/兼容快照三条差别全在函数内判，调用方不再各写一遍。③ 迁移 runner `migrateRule` 里那段 doc 字面量**没有**并进来：它的输入是旧版 `jsonRequests` 而不是 `MockRecord`，`_id` 是 `rec_<sha1(ruleId+url)>`、时间戳是合成的 `now + idx`，套同一把纯函数只会逼那条路径先伪造一个 `MockRecord`。
>
> 本卡是纯重构：`saveRecord` 行为逐字不变，diff 内零新增断言，验收靠现有用例全绿 + 用 HEAD 基线核对 strict 计数只降不升（186→184，两处落在 `src/main/repository`）。**共用只到「函数就位」为止——导入路径（R4C-15）尚未调用它，卡片说的「两条路径共用」在那一卡才算真成立。**

### D4 ID 策略：新建场景全部重生成，合并模式按 recordId

| 模式 | 规则 ID | 记录 ID |
|---|---|---|
| 新建场景（默认） | 一律 `rule_<uuid>` 重生成 | 一律 `rec_<uuid>` 重生成 |
| 合并到当前场景 | 目标规则不变 | 保留 pack 内 `id`；为空或冲突时按策略处理 |

理由：跨机导入不能撞现有 ID；而合并模式要能幂等重放同一份包（AC-R4-04「已存在的 recordId 不被修改」）。

> **落地状态（R4C-18，2026-11-20）**：两行都到代码了，但**都不是靠「导入侧先清 ID」实现的**——R4C-12 时给这条记的那笔「没有卡片承接」的账由此关闭，代价是本节原本设想的动作根本没有发生：
>
> - **新建场景**：服务层不碰包里任何一个 `id`。「记录 ID 一律重生成」是仓库那条判据的构造性后果——`importRecords` 只在包内 `id` **属于目标场景**时才当更新用（`mock.repo.ts:538-539`），刚建出来的场景一条都不属于，于是每条都走新分配 `rec_<uuid>`（有用例：包里带 `id: 'rec_from_source'`，落库后读回来的 id 不是它）。规则 ID 同理，`MockRepo.save` 对无 `_id` 的规则自己分配，服务层连 `rules[].id` 都没读。
> - **合并到目标场景**：保留包内 `id` 做幂等重放（AC-R4-04），`id` 为空或撞上时按 skip/overwrite/copy 定落点，见下面 D5/D6 与 §6.2。
>
> 归一化那半边仍然刻意不做模式分支：`mode` 是「导到哪个场景」的答案，属预览与写入阶段的入参，在 `prepareMockPackRecord` 判一次、写库再判一次就是两个决定点。
>
> **一处本节没写、实现里加了的行为**：新建模式下「整个场景一条都写不了」（包里全是阶段二拒收的坏条目）时不建那个场景，`ruleIds` 里少一个，坏条目照旧进 `invalid`——PRD 4.4.7「全部失败 → 不创建任何记录」的字面要求，留个空壳等于把库弄脏而结果页没有「空场景」这一档可交代。§7 端点表因此不能读成「新建模式恒有 `ruleId`」。

### D6 时间戳：新建取包值，合并覆盖取库内值（Q3 已裁决）

`saveRecord` 用 `Date.now()` 覆盖时间戳，而 `updatedAt` 是排序兜底键（PRD 12.1 匹配排序）。导入路径必须能注入 `createdAt/updatedAt`。代价是仓库层要接受「外部时间戳」这一新语义，因此把它限制为**仅导入路径可用**的可选参数，普通保存路径行为不变。

R4C-14 之后这件事的落点已经收窄成一个参数：doc 组装只认调用方给的 `now`，新建与更新两条分支共用同一个组装点，所以 R4C-16 只需把 `saveRecord` 里那次 `Date.now()` 换成可覆盖入参，不必再在两个分支各接一次。

**R4C-16 已落地（2026-11-20），形状与此处原设想不同**：注入点开在 `importRecords` 一侧，`saveRecord` 那次取时刻没动——卡片要求「普通 `saveRecord` 行为不变」，而「行为不变」的最低含义就是编辑器的保存永远拿本机时钟，外部给不了。落地状态见 [6.4](#64-时间戳与命中顺序必须可注入)。

注入值从哪来，按模式分（产品裁决 Q3 @2026-11-19：**覆盖取目标值**）：

| 模式 | `createdAt` / `updatedAt` | 效果 |
|---|---|---|
| 新建场景 | pack 内原值 | 复现源机的相对优先级，AC-R4-01 据此成立 |
| 合并·跳过 | 不写库，字段不动 | AC-R4-04 |
| 合并·覆盖 | **库内已有记录的值** | 本机既有优先级不因导入而重排 |
| 合并·复制为新记录 | pack 内原值 | 与新建同一规则 |
| 任一模式下 pack 值缺失 | 静默回落 `now` | 缺失不是用户的错，写入时刻本来就是缺省 |
| 任一模式下 pack 值写了却用不了 | 回落 `now` 并记 `notes`（不是 `issues`，理由见 [6.4 的落地状态](#64-时间戳与命中顺序必须可注入)） | 不让一条脏数据毁掉整包，也要让用户看见我们改了他的时间 |

两个后果必须跟着落到 UI 与测试，不能只留在这节里：

- 覆盖路径不取包值 ⇒「导出 → 合并覆盖导入 → 再导出」的时间戳不等于源包，**AC-R4-01 的往返一致性只在新建模式下成立**，测试矩阵按模式分列（见第 12 节）。
- 覆盖不动 `updatedAt` ⇒ 列表「更新时间」不变，用户会以为没生效。结果页文案写「覆盖 N 条（保持原有优先级不变）」，不给时间变化的暗示。

> **落地状态（R4C-18，2026-11-20）**：表里五行全部对上，但**服务层没有按模式传 `preserveTimestamps`**——`writeMockPackItems` 恒传 `{ preserveTimestamps: true }`（`mock.pack.service.ts:427`）。这不是偷懒，是这张表的行标签本来就不该被翻译成「一个开关」：Q3 的分模式差异已经写死在 `toRecordDoc` 的优先级里（`createdAt: existing ?? stamps ?? now`），新建分支拿包值、更新分支拿库内值，一次调用两种结果；服务层再按 `mode` 判一次就是把同一个决定做两遍，还要多写一条「传错档」的失败路径。包里没写的条目由 `toRecordDoc` 自己回落 `now`，那也不用在这里判。四行各自的落点：新建（走新建分支取包值，有用例逐字段比对）、跳过（那条压根不进 `items`，库不动，连 `updatedAt` 都没被顶——这才是「没改过它」）、覆盖（走更新分支取库内原值，用例断言 `createdAt/updatedAt` 仍是种下去的那对 `1000`）、复制（清掉 id 后走新建分支，因此与新建同一规则取包值）。**结果页那句「保持原有优先级不变」的文案仍未落地**，属 R4C-27。

### D8 校验：两阶段，包级拒整包、条目级跳单条

```
阶段一 包级：format / pack.version / 体积 / 总条数 / 顶层结构
        任一不过 → 整包拒绝，不写入任何数据
阶段二 条目级：validateMockRecord（内含 validateMatchRule）→ normalize → 上限复核
        单条不过 → 跳过并计入 issues，其余继续（4.4.7）
```

阶段二内部这半条链的顺序以**保存路径**为准，不凭推理：`MockService.saveMockRecord` 是 `validateMockRecord(:249)` → `normalizeMockRecord(:261)` → 无 match 时 `deriveMatch(:262)`，判定排在归一化之前。原图把 normalize 写在前面，会让导入接受一批编辑器保存时会拒的记录。

条目级明细通过既有 `err.issues` 通道回传（`base.router.ts:113`），不新造响应结构。

**阶段一的落地状态（R4C-10，2026-11-19）**：闸门是 `src/shared/mock.pack.ts` 的 `readMockPackText(text, byteSize)`——放在共享层而不是主进程，为的是两种部署形态读同一份判定；`byteSize` 由持有文件的一侧算好传进来（`src/main/service/mock.pack.service.ts` 的 `readMockPack` 用 `Buffer.byteLength`，只扫不分配）。四条顺序在这批定死，都不是显然的：体积排在 `JSON.parse` 之前（超限文件不该先被解析一遍才拒）；空文本与「只带普通字段、没有文件部分」（`fetchFormFileText` 回 `undefined`）都给 `packEmpty`，这正是 multipart 侧放开 `allowEmptyFiles` 时许下的原因；`version` 缺失或不是正整数算 `packFormatUnknown`，只有高于 `MOCK_PACK_VERSION` 才算 `packVersionUnsupported`——`appVersion` 全程不参与判断，只在 detail 里留着排查；总条数是跨 `rules[]` 累加，单场景都不超限的包照样要拒。接线在 `previewMockPack` / `importMockPack` 两个桩端点：过闸门之前它们对任何文件都回「成功的空结果」，现在坏包拿到的是 `errorCode`，好包当时仍回空结果桩（预览那半 R4C-13 改成真统计，写库那半 R4C-18 改成真写入，两处桩断言随之改判）。`importHar` 不吃这道闸门：HAR 顶层没有 `format`，按内容分派两种包属 R4C-21。

**阶段二的落地状态（R4C-11，2026-11-19）**：`src/shared/mock.pack.ts` 的 `validateMockPackRecords(pack)` 返回 `{valid, issues, invalidCount}`——`valid` 带包内坐标（`ruleIndex`/`recordIndex` 加原对象引用，不做副本，否则写库与冲突明细回指不到包里那条），`invalidCount` 记「跳过了几条」、`issues` 记「几项原因」，一条记录同时有几项问题时两者必然不等，混用一个数就会让结果页计数随文案改动漂移。服务侧 `readMockPack` 一次读取串完两阶段，明细现在从 `previewMockPack` 的响应体回传（R4C-13 同日落地，见下面「预览的落地状态」）：好坏混包必须仍回 `BizCode.SUCCESS`——条目级失败是数据，不是错误码；谁把它实现成抛错，`pack-validate.test.ts` 那条会先红。两条与卡片字面不符、按实现定稿的口径：① 只调 `validateMockRecord` 一处（`validateMatchRule` 已在它内部，`mock.validation.ts:146`），再包一层就是给导入开第二条标准；② `field` 保持记录内相对路径（`match.body.mode`），不拼 `records[i].` 前缀，定位已由三个坐标字段承担。另记一条与「复用同一套判定」相反的结论：**复用判定不等于把外部对象原样递进去**。`validateMockRecord` 认「无 match 但有 url」这条历史路径，靠的是 `saveMockRecord:262` 紧接着会 `deriveMatch`；而导入走仓库层（R4C-15 的 `importRecords`），那次派生压根不存在，且 `url` 本就不是包字段。所以递给判定的是按 `MockPackRecord` 契约重建的六字段视图——包内记录必须有 match，缺它就拿 `matchMissing` 跳过；放过它就正好复刻风险表 RK1「导入成功、一条不命中、全程不报错」。**代价与遗留**：判定排在归一化之前，意味着外部工具生成、只写 `method`+`path` 的包会被整条跳过（`pathTypeInvalid`+`queryOperatorInvalid`）；本程序导出的包永远带完整 match（库内记录读出来就归一化过），往返不受影响。要不要放宽是「是否支持手写包」这个产品问题，做法是把 `normalizeMatchRule` 提到判定之前，别在判定函数里为导入特事特办。

**归一化的落地状态（R4C-12，2026-11-19）**：判定之后由共享层 `prepareMockPackRecord(located)` 把包里那条变成库内形状——调的就是仓库层保存路径用的 `normalizeMockRecord`（R4C-14 后它在 `mock.docs.ts:247` 的 `recordFieldsOf` 里，之前写在 `saveRecord` 体内），自己逐字段补默认值就是第二条标准的第二个现场。它只强制两件事：`match.enabled = false`（RK6，导入不许劫持真实请求）与 `match.derivation.source = 'import'`（包里那枚印记讲的是导出那台机器的事，对本库而言这条就是导入产生的；`autoIgnoredKeys`/`suggestions`/`pathParameterized`/`analyzedAt` 原样保留，否则用户在前一台机器上调好的噪声键白丢）。三条与卡片字面不同、按实现定稿的口径：

- **「重算 `matchFingerprint`」不写回记录**：`sha1` 在 `mock.docs.ts:112`，共享层那半边要能被渲染层 import，进不去 node 内建；所以指纹由主进程 `readMockPack` 算在旁路字段 `prepared[].fingerprint` 上，只服务合并模式的预览查重（R4C-13）。真正落库那一次仓库层仍自己算（`mock.docs.ts:256` 的 `recordFieldsOf`），导入侧再写一遍就是两个写入点。
- **「缺失字段回落并计入 issues」拆成两条通道**：`issues` 只装「这条被跳过」，回落走新增的 `notes`（码 `packFieldDefaulted`，属 `MOCK_PACK_CODES`）。同一条记录可以既补齐了 `id` 又完全合法，把它记进 issues 等于在结果页把成功说成失败。
- **不生成 ID**：`mock.repo.ts:438` 那句「无 id 就 `rec_<uuid>`」是分配的唯一点，且它作为参数交给 `toRecordDoc`，组装函数自己不分号。但缺 id 必须报一声——合并模式靠包内 `id` 做幂等重放，缺了它重放同一个包就会多出副本，所以 `defaulted` 里留名，UI 侧（R4C-27）提示「重复合并将产生副本」。

**预览的落地状态（R4C-13，2026-11-19）**：`previewMockPack(source, text, options)` 落在**主进程** `mock.pack.service.ts`，不在共享层——它要读库，而共享层那半边必须能被渲染层 import。端点 `previewMockPack` 因此是四张桩里第一个不再回空结果的，`targetRuleId` 随之补进参数表。四条口径在这里定稿：

- **响应体新增必填 `notes` / `noteTotal`**：R4C-12 那条「包没写这个字段、我们按默认值补了」的通道到这里才有出口。它和 `issues` 分列两个计数，混用就会让结果页把导入成功的记录计成失败。
- **明细折叠 = 包内顺序的前 `MOCK_PACK_ISSUE_PAGE_LIMIT` 条 + 总数另报**（`pageMockPackIssues`），**不额外带一张原因分布 map**。5.4 说的「展示与存储分别定义」在这儿的落法就是这样：`issues`/`conflicts`/`notes` 三路各自分页，`issueTotal`/`conflictCount`/`noteTotal` 报真数。取前 N 而不是「每个原因留一条」，是因为明细要能回指「第几个场景的第几条」——打乱包内顺序去凑原因分布，会让人照着明细改文件却改错那条；真要逐条核对的人手里本来就拿着那个文件。
- **冲突只在目标场景内比**，且索引建在 `listRecordSummaries` 而不是 `iterateRecords` 上：指纹查重在库里就是规则级的（`findByFingerprint(ruleId, …)`），跨场景同指纹合法；而摘要只带 `_id`/`name`/`match.enabled`/指纹，用 `iterateRecords` 要把每个 ≤2MB 的响应体拉进内存再丢掉。代价写进代码注释而不藏：`_id` 是全局唯一的，「包里的 id 属于别的场景」这种必败情况预览看不见，只能等 R4C-15 写库时被 PouchDB 顶回来。
- **计数三条**：`recordCount` 是包内全量（含条目级会跳过的坏记录），「将导入 N 条」= `recordCount − invalidCount`；`variantCount` 只数将写入的那批（数坏条目的变体会让两个数对不上）；`conflictCount` 按「维度 × 条目」计，同一条记录 `_id` 与指纹都撞就算两条——但幂等重放同一个包时两个维度指回同一条库内记录，只算一条，否则「重放一次报两条冲突」会被读成两个问题。

「预览不落库」不是约定而是结构事实：`previewMockPack` 的入参类型 `MockPackSource` 只有 `listRules`/`getRule`/`countRecords`/`iterateRecords`/`listRecordSummaries` 五把，其中没有一把写得动东西。测试侧再补两重证据：假仓库的写原语被替换成「调了就抛」，以及断言调用序列里只出现读原语。**~~遗留~~（R4C-20 已销，2026-11-20）**：预览响应体里现在有「库内已有 + 待写入 + 合计档位」那三个数（`quota`，只合并模式填，见 [6.9](#69-预览把库内已有--待写入摊开档位全站仍只有一把尺r4c-20)）。原稿那句「别在预览里先造半套」的顾虑成立过一次：在写库侧那道复核（R4C-15）落地之前，预览给档位就是在造半套；现在两边读的是同一个 `recordLimitState` 与同一个 `countRecords`，才谈得上「同一把尺的两个刻度」。

### D9 HAR：不写 host 条件，只做「无证据下的保守派生」（Q2 已裁决）

单份 HAR 没有跨录制证据，因此**不执行 E1 自动忽略**，只按 `MOCK_HIGH_RISK_KEYS` 剔除 E2 高风险键并记入 `ignoreKeys`；ID 形态段**只建议参数化、不自动**（与附录 B.3 一致）。URL 拆解一律走 `shared/url.ts` 的 `parseLooseUrl`/`splitHostPort`/`normalizePathname`，**不在 HAR 解析器里重写一套 URL 逻辑**——否则会与匹配引擎的归一化结果不一致，导致「导入了却不命中」。

**`match.host` 一律留空**（裁决 Q2：HAR 的 host 不参与匹配）。这不是新增机制，只是派生时不填该字段，三处既有语义正好接住：

| 语义 | 位置 |
|---|---|
| `host === ''` → 任意 host 且任意端口 | `src/main/service/mock.matcher.ts:293` |
| 空串通过校验（只有非空才要求匹配 `HOST_REG`） | `src/shared/mock.validation.ts:222-224` |
| 空串不计入条件数，即不贡献 specificity | `src/main/service/mock.matcher.ts:262` |

代价必须显式承认，不能当成省下来的工作量：

- 一条 HAR 记录会命中同 path 的**所有环境**（测试 / 预发 / 线上），跨环境串味是用户能感知到的错。
- host 是指纹的组成部分（`canonicalMatch` 含 `normalized.host`，`mock.validation.ts:328`）⇒ 同 path 的 HAR 记录与录制记录**指纹不同，查重抓不到重复**，库里会并存两条都能命中的记录。
- 因此这类冲突只能走事后的遮蔽提示，复用既有通道：`matchWarnings`（列表接口字段，`proxy.models.ts:100`）+ `getMockMatchWarnings(ruleId)`（`proxy.api.ts:79-81`），**不新造机制、不额外增加人日**。导入结果页要显示「HAR 记录不区分域名，其中 N 条与既有规则构成遮蔽」。
- PRD 附录 B.3 原文「`match.host` = hostname（显式端口；无端口=任意）」与本裁决直接冲突，属必须回写项（第 11 节）。

### D10 入口数量：从三处收敛到两处（Q1 已裁决）

PRD 4.4.3 写了三个导出入口（规则管理器顶部 / 场景右键 / 设置→数据）。本仓库已确立「一功能一入口」，三个入口会在后续迭代被逐个裁掉。裁决结果：

- 设置 → 数据 一处（批量备份场景，语义是「全量」，与上面的「当前场景」不重复）。

去掉「场景右键/更多菜单」入口——单场景导出与顶部入口的目标对象相同，属于纯重复。PRD 4.4.3 需按此回写。

### 6.2 写入必须复用单条保存管线（推翻 PRD 4.4.6）

**问题**：PRD 4.4.6 要求「导入写入使用 PouchDB `bulkDocs`」。现有 `bulkSave()` 就是裸 `bulkDocs`（`mock.repo.ts:669`），跳过：

1. `normalizeMockRecord/normalizeMatchRule` → 包内字段残缺直接入库；
2. `fingerprintOf` → `matchFingerprint` 为空，`findByFingerprint` 查不到，**查重整体失效**；
3. `enqueueSave(ruleId)` 串行化 → 并发导入与并发保存互相踩；
4. `isRuleBlocked` 迁移闸门 → 迁移进行中写入被放行；
5. `notifyRecordChanged{upsert}` → `MockCache` 快照不更新（`mock.cache.ts:132`、`:304-326`），**导入的规则不参与命中**，且没有任何错误；
6. `record` 兼容快照（库里那条带 `record` 时由 `toRecordDoc` 续写 `toCompatRecord`，`mock.docs.ts:293`）→ 回滚旧版本时读不到。

第 5 条是本设计否决 PRD 原方案的直接理由：症状是「导入 5000 条成功，一条不生效」，且不报错。

**方案**：

- 把 `saveRecord` 里「`normalized` → `MockRecordDoc` 字段组装」抽成仓库内纯函数（含 `url` 回落、`match` 规范化、指纹、`name` 回落、`record` 兼容快照），两条路径共用一份字段逻辑。**这一步已于 R4C-14（2026-11-19）落地**，函数在 `mock.docs.ts`（`recordFieldsOf` / `toRecordDoc`），`saveRecord` 只是它的第一个调用方；下面 `importRecords` 那条因此不该再出现任何字段组装。
- 导入走仓库新方法 `importRecords(ruleId, records, opts)`：
  - 整个方法体在 `enqueueSave(ruleId)` 内 → 与单条保存共享同一把规则级串行锁；
  - 内部先做上限复核（`countRecords(ruleId) + 待写入数`），再 `findByFingerprint` 批量查重；
  - 分批 `bulkDocs`（默认 200 条/批，`_id` 与 `updatedAt` 已补齐），保留批量写的性能收益；
  - 每批完成后对**该 ruleId 调一次 `invalidate(ruleId)`**，而不是逐条发 `upsert` 事件——导入是批量语义，逐条 upsert 会让快照被重建 N 次；
  - 迁移闸门：导入期间对目标 ruleId `beginMigrationGuard`，或检测到 `isMigrationPending()` 时直接拒绝 `migrationFailed`（复用现有码）。

**缓存失效的正确性证明**是这一节唯一的硬验收：导入后立即发起一次真实请求，必须命中导入的规则。基准与回归都按此断言，不能只断言「库里查得到」。

**落地状态（R4C-15，2026-11-20）**：`MockRepo.importRecords(ruleId, records, options?)` 已落在 `src/main/repository/mock.repo.ts:495-623`，上面四条要点逐条兑现——整个方法体在 `enqueueSave(ruleId)` 内（`:499`，迁移闸门紧挨着排在它下面 `:500`）、上限复核排在查重扫描之前（`:508`）、一次摘要扫描建「指纹归属 + 本场景 `_id`」两张表（`:513-521`）、按 `MOCK_PACK_WRITE_BATCH` 分批 `pouchdb.bulkDocs` 并在每批后发一次 `{type:'invalidate', ruleId}`（`:599`、`:612`）；**没有走 `bulkSave()`**，并且这条禁令有断言钉住（把 `bulkSave` 包一层计数器）。doc 一律由 `recordFieldsOf`（`:529`）+ `toRecordDoc`（`:582`）组装，这一层没有出现字段拼装。三处按批语义改写了本节的原设想：

- **一批里一条坏数据不拖垮整批**：`recordFieldsOf` 抛出的错误码记在该条的 `failed` 上（`:530-533`），其余照写；单条保存是直接抛，这里必须换形状，否则 5000 条里一条没 match 就整包回滚，而回滚不是本卡的语义（属 R4C-19）。
- **指纹撞库内 / 撞同批前一条 → 该条不写并报 `duplicate`**（`:541-545`）。跳过 / 覆盖 / 复制三策略仍属 R4C-18 在服务层选，这一层只保证「改批量写不会绕过指纹唯一」这条不变量——并发两次导入同一份包，只有一条落库（有用例）。
- **包内 `id` 只在确实落在本场景时才当更新用**（`:538-539`），否则一律新分配 `rec_<uuid>`。这一条是本节没写到但必须补的安全边界：全盘接受包内 id 的话，手改过的包能拿**别的场景甚至规则文档**的 `_id` 盖掉库内文档（`_id` 全局唯一，`rec_` 之外还有一整类规则文档）。附带把 R4C-13 记下的「跨场景 id 预览看不见」那条取舍落地为**不在预览查全库 id**：写入侧另发新 id 消化掉，来源那条不动。

时间戳自 R4C-16 起不再是「整批一个 `now`」：`options.preserveTimestamps` 是只开给导入路径的注入口子（组装处 `:573-581`），新建取包值、覆盖取库内原值，落地状态见 6.4；取消、进度、回滚（6.5）没做，属 R4C-19。**服务层编排已于 R4C-18 接上**（[6.6](#66-合并冲突四象限三策略推翻-prd-444-的那张矩阵)）——`/_appmock/importMockPack` 不再回空结果桩，渲染层拿得到写入能力了，但它还没有调用方（导入弹窗属 R4C-25~27）。

### 6.3 导出组装

- 单场景：`getRule(ruleId)` + `iterateRecords(ruleId, visitor, 200)`（不受列表分页上限约束，`mock.repo.ts:362-370`）。
- 全场景：先用 `MockRepo.listRules()` 拿**全部**规则（`search()` 的 `RULE_SEARCH_LIMIT = 15` 会把第 16 个之后的场景静默漏掉，且它按命中数排序、这里没有排序依据），再逐场景走同一段循环。
- **原前提「流式拼接字符串就能压住内存峰值」已被 5,000 条基准证伪**（`test/bench/pack-export.bench.ts`，三档各起一个进程）。只要出口是「返回完整字符串」，峰值下界就是包体积的两倍上下——分片缓冲一份、最后 `join`/`stringify` 的完整副本一份，**分片与聚合两种写法在峰值上没有差别**：

| 5,000 条 / 8KB 体（包 42.7MB） | 每页采样的活堆高水位 | 收尾活堆高水位（含最后一次 join/stringify） | 交还后残留 | 耗时 |
|---|---|---|---|---|
| 聚合成对象再一次性 `stringify` | +44.6MB（**漏采**：stringify 发生在最后一页之后） | **+85.5MB** | +85.5MB | 240ms |
| 流式拼接 + 返回字符串（R4C-06 落地的写法） | +85.7MB | **+85.5MB** | +85.5MB | 212ms |
| 流式拼接 + 直接写盘（R4C-08 采用的桌面端出口） | +2.2MB | **+0.2MB** | **+0.3MB** | 283ms |

  - 差别的唯一来源是**出口**：结果交还给调用方之前那份完整副本是否存在。落盘档的 2.2MB 是写缓冲 + 每页 200 条记录的活引用，**不随包大小走**，代价只有耗时 +30%。
  - 「每页采样」这一列必须和「收尾」一起看：只报每页高水位会让聚合档看起来比流式档省一半，实际两档收尾都是 85.5MB。基准因此同时量两次（`liveMb` / `endMb`），文档引用内存数字时必须引 `endMb`。
  - 因此本节的硬结论改为：**桌面端导出不走「组装返回字符串」**，改由主进程边拼边写目标文件（见 [D2](#d2-文件写出主进程组装--主进程弹框落盘返回值三态) 与任务拆分 R4C-06/R4C-08）。字符串出口只保留给 Web 分支。
- 空场景（AC-R4-10「不遗漏空场景」）：只要规则在 `listRules()` 里就写出 `"records":[]`，**判据不得是「该场景有记录」**——否则导入侧无法区分「场景是空的」与「场景没导」，UI 也无从回显条数。单测 `一个场景都没有也是合法包` / `空场景留在包里` 各守一头。
- 变体、响应体按库内原样写出；`sanitizeResponseHeaders` 用于录制回填路径，导出**不做**逐跳头过滤（保留用户配置的完整响应头），与既有「保存只校验、发送才过滤」的分工一致。

### 6.4 时间戳与命中顺序（必须可注入）

`importRecords` 增加 `preserveTimestamps` 语义（仅导入路径使用）：写入包内 `createdAt/updatedAt`，缺失或非法（非数字、超范围）时回落 `now` 并记入 issues。普通 `saveRecord` 行为不变。

配套（Q3 已裁决，见 [D6](#d6-时间戳新建取包值合并覆盖取库内值q3-已裁决)）：合并模式的「覆盖」分支不取包值，而是**读库内已有记录的 `createdAt/updatedAt` 原样写回**——即注入点仍然要用，只是喂进去的是目标值而不是源值。实现上这意味着覆盖分支必须先把现有 doc 读出来，不能直接拿 pack 里的对象覆盖。

因此 AC-R4-01「导出→导入→再导出逐字段一致」的适用范围收窄为**新建场景模式**；合并覆盖模式的往返定义是「内容一致、时间戳保持库内原值」。这条边界要同时写进 PRD 4.4.4、测试矩阵和发布说明，否则测试会在合并模式下报一个「预期失败」。

**落地状态（R4C-16，2026-11-20）**：注入点开在两处，但判定只有一份。共享层 `packTimestampOf(value)`（`src/shared/mock.pack.ts:211-215`）认「可用的正整数毫秒」，`Number.isSafeInteger` 之外再加一条 `Date` 上界——`updatedAt` 是列表与匹配排序的兜底键，坏值留在库里比丢掉更难查。三个消费方各取所需：
- `prepareMockPackRecord` 用它把包值清成「可用值或 `0`」，于是交给写入侧的记录里再没有字符串与越界数；**写了却用不了**时把字段名推进 `defaulted`，经 `readMockPack` 折成预览的 `notes`（`packFieldDefaulted`，文案随本批改写成覆盖「没给」与「不可用」两种）。包里没作则不作声——缺失不是用户的错，写入时刻本来就是缺省。
- `importRecords` 的 `options.preserveTimestamps`（`mock.repo.ts:573-581`）再判一次，只为兜住没经过归一化层的调用方（HAR 与直接用仓库的测试），`0` 与「没写」同义 → 落 `now`。
- `toRecordDoc` 多一个 `stamps` 入参（`mock.docs.ts:275`）：`createdAt` 排在 `existing?.createdAt` **之后**——库里有就不动，这一条优先级就是 Q3「覆盖取目标值」的落点，注入也翻不掉它；`updatedAt` 排在 `now` 之前。

三种模式因此在仓库层各有确定形状：新建取包值、覆盖取库内原值（连 `updatedAt` 都不顶，列表「更新时间」不变）、跳过不写。**与卡片字面不同**：回落记的是 `notes` 而不是 `issues`，沿用 R4C-12 定下的通道——进 `issues` 会让结果页把成功写入计成失败。

**R4C-18 已接上调用方**（2026-11-20）：导入编排对每一批都传 `{ preserveTimestamps: true }`（`mock.pack.service.ts:427`），**不按模式分支**——Q3 的分模式差异已经在上面那条优先级里，服务层再判一次就是第二个决定点（详见 [D6 的落地状态](#d6-时间戳新建取包值合并覆盖取库内值q3-已裁决)）。「复制为新记录」也确实复用了新建那支（清 id 后走新建分支，因此取包值）。**仍缺两条**：AC-R4-01 的往返用例属 R4C-31；预览/导入前的「库内已有 + 待写入」合计上限提示属 R4C-20，目前只有仓库侧那句偏保守的 `countRecords + 本批条数` 上界在挡。

### 6.5 取消、进度与回滚

- 取消：沿用仓库既有的 `AbortController` 单例模式（更新链路 `src/main/update.runner.ts:25-39` 已是同一形状），导入任务同样单例——并发导入互相写同一规则比慢更糟。
- 进度：按「已写入批次数 / 总批次数」，不做字节级进度（条数才是用户关心的单位）。
- 回滚：新建场景模式下失败即 `delete(newRuleId)`（该方法已含记录清理 + 缓存失效 + `lastActiveRuleId` 处理，`mock.repo.ts:245-258`）；合并模式不回滚已写条目，结果页明确标注「部分写入，保留 N 条」。

**落地状态（R4C-19，2026-11-20）**：三件事都接上了，但接的位置各不相同，别把它们读成一层。

- **取消落在仓库的批与批之间**（`mock.repo.ts:590-596`），不落进服务层：分批循环只在 `importRecords` 里有，服务层再切一遍就是第二套分批口径。信号由 `MockPackService` 的单例持有，经 `MockPackImportRuntime`（`mock.pack.service.ts:59-63`）递进来，`writeMockPackItems` 原样交给仓库（`:457`）。这个 runtime 刻意不并进 `MockPackImportOptions`：那个类型是端点能收的 query，`AbortSignal` 与回调既序列化不过去，也不该由客户端指定——与 `preserveTimestamps` 不当入参是同一条理由。
- **取消的语义是「已写的一条不动，没写的每条有交代」**：剩下的批次一条都不写，但每个未写条目仍以 `packWriteAborted` 进 `outcomes`（`:593`），结果里另加 `aborted` 一栏。`aborted` 与 `partial` 是两回事——取消发生在首批之前时 `partial` 为假（库里一个字没动）而 `aborted` 为真，混成一个布尔就没法区分「没写完」与「写坏了」。
- **进度按批次**：每写完一批 `onBatch(batch+1, totalBatches)`（`:613`），单例把它记在任务状态里，`getImportProgress()` 回 `{running, written, total}`（`mock.pack.service.ts:656`）。**读数口径是「当前这个场景的第几批 / 共几批」**：分批只发生在仓库那一层，新建模式几个场景就重置几次，跨场景累计没人算——已有用例把这个形状钉死了（`[[1,2],[2,2],[1,1]]`），因为渲染层要哪种口径属 R4C-26/27 尚未裁决。
- **回滚只回收新建模式的空壳**，判据是「本场景实际写进去几条」而不是「有没有 `failed`」（`mock.pack.service.ts:503-513`）：零写入就 `source.delete(ruleId)`（仓库那句 `delete`，现位 `mock.repo.ts:257-270`，卡片里写的 `:245-258` 是当时的行号——它已含记录清理、`{type:'remove'}` 缓存通知与 `lastActiveRuleId` 复位，服务层不许自己补任何一步），且这个场景不进 `ruleIds`：`ruleIds` 是结果页「跳到哪几个场景」的入口，留个空壳进去等于让用户点进一个什么都没有的场景。整批被拒（`recordTooMany`、迁移闸门）与取消落在首批之前是同一种局面，都走这条回收；写进去过一条就不回收（AC-R4-09「已成功条目保留」）。合并模式永不回滚，目标场景是用户自己的。
- **并发导入直接报错，不静默忽略**：`mock.pack.service.ts:626` 拿 `packImportInProgress` 拒绝第二个请求。形状抄 `update.runner.ts:25-39`，但那一层没人盯着、重复请求可以忽略，导入这条是用户按下按钮等结果的，弹窗挂在「等一个不存在的取消按钮」上比报错难交代。抛错与包级闸门没过都在 `finally` 里交还槽位（`:638`），有两条用例分别钉「占住」与「交还」。

两条边界要说清：**取消与进度目前只到服务层，端点上还没有它们的通道**——`cancelImport()` / `getImportProgress()` 在 `src/` 里没有任何调用方，走 IPC 还是 HTTP 推、渲染层显示成什么，都属 R4C-26/27；本批不替 UI 决定通道。另一点：回收判据看的是实际写入，所以「条目级全坏 ⇒ 一条都写不了」那一档仍由 R4C-18 的「不建空场景」那条路径负责（`items.length === 0` 时根本不 `save`），两者合起来才是「库里不留空壳」。

用例：`test/migration/pack-import-cancel.test.ts`（真 PouchDB，8 条）+ `test/unit/pack-import-cancel.test.ts`（假写源，4 条）。七处「改坏实现 → 用例必须变红 → 回滚」的实测落点，红的位置正好把三层的分工摊开：

### 6.6 合并冲突四象限 × 三策略（补齐 PRD 4.4.4 欠的那张矩阵）

PRD 4.4.4 只写了「按 recordId」，而判定有两个互不等价的维度（`_id` 与 `matchFingerprint`），逐格定义是它自己在 §11 差异表里欠下的账。R4C-18 把矩阵落到 `placeMockPackRecord`（`mock.pack.service.ts:379-402`），「算不算撞」则只有 `classifyMockPackClash`（`:304-308`）一份实现，预览与导入共用（`:355`、`:492`）——分两处算就是两套标准，症状与包校验开第二条标准时一样。

| 象限（合并模式） | `skip` | `overwrite` | `copy` |
|---|---|---|---|
| 都不撞 | 写（新建分支，取包值） | 同左 | 同左 |
| 同 `_id` **且**同指纹（重放同一个包） | `skipped/packIdCollision`：**一条都不写**，连 `updatedAt` 都不顶 | 按 ID 覆盖：内容真换，时间戳仍是库内原值（Q3） | 交回仓库分配 ID ⇒ 撞指纹 ⇒ `skipped/matchDuplicate` |
| 同 `_id`、条件换了 | `skipped/packIdCollision` | 按 ID 精确覆盖那一条（改的就是它的匹配条件），条数不变 | 新 ID 另建，库里两条并存 |
| ID 不撞、指纹被库里**另一条**占住 | `skipped/matchDuplicate` | **覆盖占住指纹的那条**，不是包里 id 指的那条 | `skipped/matchDuplicate` |

四格里有三格的答案不是显然的，都是被同一条不变量逼出来的：**库里不能留下同指纹的一对**。`MockRepo.saveRecord` 的指纹查重（`mock.repo.ts:430-433`）是代码级判据、不是唯一索引，所以「塞进去」不会当场报错，但此后那两条在编辑器里谁都存不下——用户改一条就吃 `matchDuplicate`，改另一条也吃，等于静默弄坏两条既有记录。于是：

- **覆盖取「指纹优先于 ID」**：包里那条挂着 A 的 id、却是 B 的条件时，落点是 B（`clash.sameFingerprint?._id ?? item.record.id`）。按字面「按 recordId 覆盖」写会正好造出那对存不下的记录，这一格有用例逐条验（库里两条指纹数仍为 2、A 那条一个字没动）。
- **复制不开「同指纹也硬写一份」这条路**：`copy` 只是把 id 交回仓库那唯一一次分配，撞不撞由仓库那把查重裁决。PRD 那句话读成「无论如何都另建一条」是做不到也不该做的——本卡因此只覆盖四象限中「条件真的换了」那一半，同条件的那一半报跳过，用例里额外用 `repo.saveRecord` 改一次名来证明库里那条仍存得动。
- **纯重放也算撞**：内容一样照样走一次写库会把 `updatedAt` 顶成现在，而 AC-R4-04 要的是「已存在的 recordId 不被修改」。只有不动它才叫没改过，所以跳过档不看内容看 ID。

两条取值口径一并定死：

- **认不出的策略落回 `skip`**，两处各管一段：路由层 `toMockPackConflictStrategy`（`mock.pack.ts:263-273`）把 query 字符串收敛到三种取值，服务层的分支默认档也落回跳过（`mock.pack.service.ts:393-401`）。三种策略里只有 skip 是安全的——拼错一个字母就盖掉库内数据，比漏跳几条难发现得多。这里不复用「缺省即默认」那种写法去猜 `copy`。
- **`skipped[]` 明细必须带包内坐标**：一个包可以有多个场景，只给 `recordIndex` 指不回文件里哪一行，所以 `MockPackSkipped` 补了 `ruleIndex`；`reason` 分两种（`packIdCollision` 新增码 + 复用 `matchDuplicate`），`detail` 写清撞的是库里哪条 id。仓库逐条结果里那些没写成功的条目由 `writeMockPackItems` 折算成同一形状（`:415-448`），响应体的 `created`/`updated` 直接取仓库那两栏，不在服务层重算一遍 ID。

### 6.7 导入即生效要作废的是四层，不止快照

「导入成功但一条都不命中」不是单一故障：从包写进库到请求真的命中，中间有四层，每一层都可能留着旧答案。本节就是 PRD 4.4.8 新增的 **AC-R4-11** 的验收落点（也是 4.4.6「禁止裸 `bulkDocs`」那条禁令的验收对象）。R4C-15 只交付了第一层的事件形状，这里把四层各钉一条运行时断言（`test/migration/pack-import-cache.test.ts`，真 PouchDB + 真 `MockCache`，服务层编排 `importMockPack` 打进去，不手工调仓库原语伪造导入）。**验到 `MockCache` 那层为止**：再往上的 `MockService.mock` 透传（`activeRuleOf` → `effectiveResponse` → `requestEnd`）没有用例、本批也没补，AC-R4-11 那句「由导入的记录返回 Mock 响应」的最后一跳只能在打包后真机冒烟。

| 层 | 留着旧答案的症状 | 谁负责作废 | 钉它的用例 |
|---|---|---|---|
| 快照（编译后的候选集） | 导入的记录要等重启才参与命中 | `invalidate` 事件 → `MockCache.invalidate(ruleId)`（`mock.cache.ts:254-258`、`:311-313`） | 写库前 `snapshotCount` 由 1 掉到 0，重建只发生在下一次请求（`compiledBuilds` 1→2），且 `incrementalUpserts` 恒 0 |
| memo（同一请求的判定结果） | **启用之后仍回答「不命中」**——四层里最难发现的一条：库和快照都对了，命中还是错的 | `upsert` 分支末尾 `snapshot.memo.clear()`（`mock.cache.ts:238`） | 导入后先 miss 一次（memo 存下这条 miss）→ `saveRecord` 翻 `enabled` → 第一次 match 必须 `matched:true` |
| 响应缓存（LRU，按 recordId） | 覆盖导入换了响应体，端上拿回的还是覆盖前那段文本 | `invalidateResponsesOfRule`（`mock.cache.ts:525-529`，随 `invalidate` 一起走） | 预热响应缓存 → 重放同一个包只改 body → 下一次取响应拿到新文本，且库里仍只有一条 |
| 场景启用状态（`lastActiveRuleId`） | 导入把用户正在用的场景切走，等于绕过「导入不自动启用」 | 导入路径不写它（D5：唯一写者是 `setLastActiveRuleId`） | 先把它指向另一个场景 → 新建模式导入 → 读回仍是原值；包里写 `enabled:true` 落库仍是停用且不命中 |

「**匹配过程不回读库**」这句口径要限定清楚，否则断言会写成一句假话：`match()` 只读快照，而响应体本来就交给按需回源（快照不带 body 是 §2 的代码事实）。所以能钉的是**次数**而不是「零」——把 `listRecordSummaries` / `getRecordById` 包上计数器后写死三个读数：启用之后第一次命中 `{summaries:0, byId:0}`（走增量维护，一次库读都没有），取响应体那一次 `{byId:1}`，同请求再命中 `{summaries:0, byId:0}`（memo + LRU 都在）。源码级护栏（`match()` 体内不许出现 `mockRepo`/`pouchdb` 字样）已经在 `test/bench/matcher.bench.ts:204-218`，两边不重复、各管一段。

三条用例做过变异校验（改坏实现 → 用例必须变红 → 回滚）：注掉 `onRecordChanged` 的 `invalidate` 分支 ⇒ 快照层与响应缓存层两条变红（读数分别停在 1 与「旧文本」）；去掉 `memo.clear()` ⇒ 启用那条变红（`matched` 停在 `false`）；把批量写的一次 `invalidate` 改成逐条 `upsert` ⇒ 事件序列那条变红。

### 6.8 批量写让整场景 `createdAt` 同值，按它翻页会漏条（R4C-19 撞出来，R4C-34 修掉）

R4C-19 的用例要证明「取消后写进去的就是批内前 200 条」，得把那些记录回读出来。用 `iterateRecords` 回读时读数对不上：库里 `countRecords` 明明是 200，枚举只回来 100 条。换按 ID 直接回取（`readDocs({keys})`）就全对上了——所以不是写入少了，是**枚举漏了**。

根因：`importRecords` 整批共用一个 `now`（`mock.repo.ts:549`，R4C-15 的批语义），于是一个场景里批量写入的记录 `createdAt` 全等；而四条读路都用 `sort: ['type','ruleId','createdAt']` + PouchDB 的 `bookmark` 翻页，排序键有并列时 bookmark **下一页返回空、bookmark 直接给 null**——调用方只看到「读完了」，实际只拿到第一页，没有任何错误码。

2026-11-20 实测（临时库，一次 `importRecords` 写 1,200 条到同一个场景）：

| 读法 | 修前 | 修后 |
|---|---|---|
| `iterateRecords`（默认 pageSize=100） | **100** | 1,200 |
| `assembleMockPack` 的 `recordCount`（导出用 `PACK_EXPORT_PAGE_SIZE=200`） | **200** | 1,200 |
| `listRecordSummaries`（默认 500 / 传 200） | **500 / 200** | 1,200 |
| `listAllRecordSummaries`（默认 500） | **500** | 1,200 |
| `countRecords`（页大小 1,000） | **1,000** | 1,200 |
| 与第 1,150 条同指纹的记录导入 | **报 `created`（重复入库）** | 报 `duplicate` |

两个补充读数决定了修法的取舍：①**并列不必整批同值才触发**——另造一批 250 条、`createdAt` 只取 7 种不同值，pageSize=100 照样只读回 100 条，页边界落在任一并列上就截断。②`listAllRecordSummaries` 只按 `['type']` 排序，全库一旦超过页大小 500 就必然只读回 500 条，**这是 R4 之前就存在的存量缺陷**（消费方 `mock.migration.runner.ts:162`），与本次批量写无关，同批一起修掉了。

漏读的实际后果不止「导出少条」：`importRecords` 的上限复核（现位 `:508`，R4C-20 把它改成读 `recordLimitState` 时往后推了两行）和指纹查重扫描（现位 `:516`）都骑在同一条读路上，所以库里第 501 条之后的记录**既不参与查重、也不计入上限**——同一个包重复导入会把已有记录再写一份，`MOCK_RECORD_REJECT_LIMIT` 也能被绕过。

修法试了三个，只留下一个：

| 方案 | 实测结果 |
|---|---|
| 排序键补 `_id` 做 tie-break | **走不通**。记录索引是 `['type','ruleId','createdAt']`（`:109-123`），mango 要求排序键是索引前缀，补 `_id` 就得重建含 `_id` 的索引，而 `createIndex` 不接受 `_id` 字段（直接报 `Cannot convert undefined or null to object`） |
| 按 `_id` 游标翻页（`selector._id > 上一页末条` + `sort: ['_id']`） | **完整但更慢、且丢时间序**。1,200 / 5,000 条都读得全；2 万条 × 页大小 1,000 实测 5.9s，比 `skip` 的 2.4s 慢一倍以上（`sort` 选不到记录索引），而且结果变成 `_id` 序——新记录 `_id` 是随机 UUID，导出顺序会从时间升序变成乱序，要自己再排一遍 |
| `skip` 一路翻到某一页不满 | **采用**。250 条并列、5,000、2 万条三种数据下都读得全且无重复；顺序仍是 `createdAt` 升序，消费方（导出/预览/缓存/迁移）行为不变；2 万条 × 页大小 1,000 实测 2.4s |

落地形态是 `mock.repo.ts:288` 的私有 `eachRecordPage(request, pageSize, onPage)`：一条翻页循环，`countRecords`(`:304`)、`listRecordSummaries`(`:330`)、`listAllRecordSummaries`(`:340`)、`iterateRecords`(`:362`) 四个读路都从它取，逐页回调所以 `iterateRecords` 仍是流式（不把整批读进内存，导出/基准的内存结论不受影响）。`listRecords`(`:381`) 本来就是 `skip`（UI 要随机跳页），只把排序键换成同一个 `RECORD_SORT` 常量，注释里原来那句「改用 bookmark 能消掉窗口漂移」已被本轮实测证伪，改成「不能用 bookmark，并列会截断」。`countRecords` 不带 `ruleId` 那一支仍走 `allDocs` 的 key 区间，与 find 无关，本批没动。另有一条 `listAllRecords`(`:352`) 委托给 `iterateRecords`，所以顺带修好；它实测**全工程零调用方**（`src/` 与 `test/` 都搜不到，R4 之前就存在的死代码，本批仍不删，等裁决）。

代价说清楚：`skip` 翻页期间若有新写入或回滚落在窗口之前，页会漂移（重复或漏看），读到的不保证是同一时刻的快照——这与修前 bookmark 的语义同级（bookmark 本来也只是理论上的快照稳定），对「数条数 / 建查重索引 / 导出整批」这三个用途，误差量级远小于用途本身。

验证：`test/migration/repo-record-paging.test.ts` 8 例（真 PouchDB + 临时库，1,200 条一批）。修前 7 红 1 绿，红的读数就是上表；第一个用例断言「这批确实共用一个 `createdAt`」，将来哪天 `now` 改成每条取一次，这个前提会先失效报警，而不是让整组用例悄悄退化成空断言。R4C-19 那批用 `iterateRecords` 读数的小用例（`pack-import-service.test.ts:75-79`、`pack-import-cache.test.ts:100`）不用改；`pack-import-cancel.test.ts` 顶部「不走 iterateRecords」的注释已随本批更新（读法保留，但理由不再成立）。闸门：tsc 0 错、单测 427、迁移 77（+8）、`check:strict` 未收口 184→180（删掉四处 `const request: any`）、`build:web` 通过、`--target=bench` 达标且导出基准三档耗时 165/245/202ms。**打包未验**（本机 `app.asar` EBUSY）、**真机未验**。

### 6.9 预览把「库内已有 + 待写入」摊开，档位全站仍只有一把尺（R4C-20）

**为什么要多读一次库**：两个数里「待写入」包里就有（`recordCount − invalidCount`），「库内已有」只能问仓库。R4C-18 之前只有写库那一步拦得住院子，用户在弹窗里看到的「将导入 3,000 条」并不知道目标场景已经躺着 8,000 条——越界的那一次导入本来会整批被拒（`recordTooMany`），但那是**写完才说的拒绝**，不是**点写之前的警告**。

**判据只有一处**：档位（5,000 提示 / 10,000 拒绝）复用库内既有上限提示那一份 `recordLimitState`（`src/shared/mock.models.ts:402-412`，缓存侧 `getLimitState` 也读它）；包侧新加的 `mockPackQuotaOf`（`src/shared/mock.pack.ts:155`）只做「把两个数相加 + 把两个数一起摊出来」这一件事。顺带把仓库 `importRecords` 里手写的 `total + records.length > MOCK_RECORD_REJECT_LIMIT`（现位 `src/main/repository/mock.repo.ts:504-511`）改成读同一把尺——**留两处写法，改阈值的人只会改到一处**。

**三个数分别是什么**：`existingRecordCount` 是目标场景的真数（`countRecords`），`incomingRecordCount` **等于同一个响应体里的 `recordCount − invalidCount`**（不是第三套计数，用例把这个恒等式钉住了），`totalRecordCount` 是两者相加、档位拿它比。预览显示「将导入 3,000 条」同时又说「待写入 3,005 条」这种自相矛盾，只有两套计数才会产生。

**它是上界而不是净值**：跳过与覆盖都不新增条目，而预览在用户改策略之前就要给数，所以 `incomingRecordCount` 按「有效记录全部新增」算。方向是安全的——仓库复核拿的是真正提交给它的条数（恒 ≤ 预览那个数），于是**预览只会提前警告，不会漏报**；反过来按净值算就会出现「预览里看不见、导入时却被整批拒」。

**只有合并模式填**：新建模式没有目标场景，`countRecords` 读回来的数属于谁都没定义；更根本的是包级闸门 `MOCK_PACK_MAX_RECORDS`(5,000) 判的是**整包记录总数**（`mock.pack.ts` 阶段一那条 `recordCount > MOCK_PACK_MAX_RECORDS`），超过就整包拒绝，而建议档的判据是「> 5,000」——**新建模式在算术上够不到任何一档**。所以 `quota` 是可选项，用例还断言新建模式连 `countRecords` 都不该被调（为不填的字段多读一次库，是白付的钱）。

**没有在服务层再拦一次**：卡片原句「把分场景的合计口径从仓库上提到服务层」按「口径同源」落地（两处读同一个 `recordLimitState`、同一个 `countRecords`），**拦截点仍只保留仓库那一个**。服务层再判一次不会多拦住任何东西（它拿到的条数与仓库那句完全相同），却会多出两个可以说「不」的地方，将来改判据的人只会改其中一个。

**未做**：`importMockPack` 的响应体不带 `quota`（结果页要显示这两个数，复用预览那次读数即可，要另立口径得先裁决）；渲染层还没有消费方（R4C-26/27），`splitRecommended` / `recordTooMany` 两档的人话文案尚未接线。

验证：单测 5 例（`test/unit/pack-preview.test.ts`，边界取「合计正好 5,000 / 10,000 都不亮」——判据是「大于」不是「不小于」）+ 真库 2 例（`test/migration/pack-preview-quota.test.ts`：隔壁场景的 5 条不进合计、填档位没把预览变成写库）。闸门：tsc 0 错、单测 427→432、迁移 77→79、`check:strict` 未收口 180（0 新增）、`build:web` 通过。

## 7. 接口设计

新增端点（命名按仓库现行约定用 UPPER_SNAKE 键；旧端点是 PascalCase，不重命名以免扩大改动面）：

| 端点 | 方法 | 参数 | 返回 |
|---|---|---|---|
| `/_appmock/exportMockPack` | GET | `ruleId?`（省略=全部）、`scope`、`includeSource`、`redact`、`includeVariants` | 桌面端：仅用于 Web 分支，返回包文本；桌面走 IPC 不请求此端点 |
| `/_appmock/previewMockPack` | POST | multipart 文件 + `mode`、`targetRuleId` | `{kind, packVersion, appVersion, ruleCount, recordCount, variantCount, invalidCount, conflictCount, issues[], issueTotal, conflicts[], notes[], noteTotal, suggestedRuleName?, quota?}`，**不落库**（R4C-13）；`quota` 是「库内已有 + 待写入 + 档位」三个数，仅合并模式填（R4C-20，见 6.9） |
| `/_appmock/importMockPack` | POST | multipart 文件 + `mode`、`targetRuleId`、`conflict` | `{ruleIds[], mode, created[], updated[], skipped[], invalid[], failed[], invalidTotal, enabled: false, nameCollided, partial, aborted}`（R4C-18） |
| `/_appmock/importHar` | POST | multipart 文件 + `mode`、`targetRuleId` | 同上 + `suggestions[]`（Path 参数化建议） |

三个写端点全部要求 handler **返回对象而非 `undefined`**（`base.router.ts:94-98` 的陷阱），空结果也要回 `{created: [], ...}`。

两处与原表不同，按 R4C-18 的实现定稿：

- **`preserveTimestamps` 不是客户端入参**。原表把它列进 `importMockPack` 的 query，等于让调用方决定「要不要保住源机优先级」——而 Q3 已经裁决过这件事，客户端再给一次就给了它翻掉裁决的口子（且给 `false` 会让覆盖分支把库内 `updatedAt` 顶成现在，正是 Q3 要避免的症状）。现在它是服务层写死的一条内部约定（恒 `true`），query 只收 `mode`/`targetRuleId`/`conflict` 三项，`conflict` 经 `toMockPackConflictStrategy` 收敛后才交给编排层。
- **`ruleId` 单数改成 `ruleIds` 复数**。新建模式是「为每个导入场景建一个新规则」（PRD 4.4.4），一个 N 场景的包就有 N 个新场景，单数字段既装不下也没法告诉结果页「前往启用」该跳哪几个；合并模式恒为一个（目标场景，即使一条都没写也回它，AC-R4-04 的「重放同一个包」要看得到落点）。另外「全坏场景不建壳」意味着 `ruleIds.length` 不等于包内场景数，UI 不能拿它反推场景数（用例见 `test/migration/pack-import-service.test.ts`）。

新增错误码（`src/shared/mock.errors.ts` 第四组 `MOCK_PACK_CODES`，随 `MOCK_ERROR_CODES` 派生；**每个码同时补 zh-CN / en**）：

| 码 | 语义 | 层级 |

| `packFormatUnknown` | 不是规则包/HAR | 包级 |
| `packVersionUnsupported` | 版本高于当前 | 包级 |
| `packTooLarge` | 超过 50MB | 包级 |
| `packRecordLimit` | 包内记录 > 5,000 | 包级 |

| `harBodyUnreadable` | 响应体读不出字节：`text` 缺失但 `size > 0`（R4C-21），或判成二进制却没有 base64 标记（R4C-23） | 条目级（跳过） |

条目级原因的展示分两族，**按 code 落在哪一族取文案，不在界面侧再判一次**（R4C-11 落地时回写本段，原稿把两族混成了一句「条目级走 `mock.pack.<code>`」）：

| 明细来源 | code 族 | 文案块 | 为什么 |
|---|---|---|---|
| 阶段二逐条判定（`bodyTooLarge`/`variantLimit`/`bodyModeUnsupported`/`matchMissing`/`statusRange`…） | `MOCK_VALIDATION_CODES` | **`mock.editor.validation.<code>`（复用，不新增）** | 阶段二调的就是保存路径那一个 `validateMockRecord`，同一份判定必须是同一份文案；再抄一份到 `mock.pack.*` 就会出现「同一原因在编辑器和导入弹窗说两种话」 |
| 包级与 HAR（`packFormatUnknown`/`packVersionUnsupported`/`packTooLarge`/`packRecordLimit`/`packEmpty`/`har*`） | `MOCK_PACK_CODES` | `mock.pack.<code>` 新块 | 这些原因只在文件侧能修，编辑器里压根没有对应输入 |

`packFieldDefaulted`（R4C-12）也在 `MOCK_PACK_CODES` 这一族，但它**不是失败**：它挂在 `readMockPack()` 的 `notes` 通道上，讲的是「包没写这个字段、我们按默认值补了」，条目照样导入。混进 `issues` 会让结果页把成功的记录计成失败。这条通道自 R4C-13 起有出口——预览响应体的 `notes`/`noteTotal`，渲染层拿它出「已按默认值补齐 N 项」而不是「失败 N 条」。

两族互斥、且各自的键集都有断言兜着（`test/unit/pack-errors.test.ts`）：`MOCK_PACK_CODES` 不得出现在 `mock.editor.validation` 里，中英两侧的 `mock.pack` 键集必须与 `MOCK_PACK_CODES` 完全相等，且 `MOCK_VALIDATION_CODES` 每一项在中英 `mock.editor.validation` 下都有非空文案（失败消息里报出键数与码数，防「覆盖看起来做了其实漏了一半」）。按 `src/lang/zh-CN.ts:274-276` 已记录的教训，动态拼键 `$t('mock.pack.' + code)` 无 `te()` 兜底时会直接显示键名，所以新增码必须成对补文案——闸门已存在，不再需要假设。

## 9. HAR 解析细则

映射按附录 B.3，以下是实现必须处理的真实世界形态：

| 形态 | 处理 |
|---|---|
| `content.text` 且 `encoding === 'base64'` | 分两档：文本档（json/xml/text）用 `base64ToText` 解成文本存、`bodyEncoding` 留空，编辑器可直接改；binary 档原样存 base64 + `bodyEncoding='base64'`（AC-R4-07）。解不出合法 UTF-8 时按 binary 处理——`mimeType` 报的「文本」其实不是文本，照文本存发出去就是乱码 |
| 折行 base64（Chrome / Fiddler 每 76 字符换行） | 不需要预处理：`atob` 自己跳过 ASCII 空白，实测折行样本与单行样本解出同一份文本。真正会抛的只有中段 `=` 的拼接式 base64 与非 UTF-8 字节，两者都落上一句的 binary 档 |
| `content.text` 存在、`inferBodyType` 判成 binary，却没有 base64 标记 | 条目跳过 `harBodyUnreadable`（R4C-23）：HAR 把字节当文本写了，无论按文本还是按 base64 存，命中后回去的都是坏字节。detail 带 `encoding=` 与 `mimeType=`，与「`text` 缺失但 `size > 0`」同一个码、不同的一半成因 |
| 响应体 > 2MB | **不在映射层判**：阶段二那把 `validateResponseDef`（`src/shared/mock.validation.ts:120`）量的就是解码后的 UTF-8 字节，报 `bodyTooLarge`；映射层再加一道就是第二条标准。卡片（R4C-23）字面的「2MB 校验」由此承接 |
| `content.text` 缺失但 `content.size > 0` | 条目跳过 `harBodyUnreadable`——Chrome 对二进制资源常不记录正文，这是常态不是异常 |
| `postData.params` 而非 `postData.text` | **不入库**（R4C-22 裁决）：B.3 写的落点 `source.requestBody` 在模型里不存在，且全站没有任何界面读 Mock 记录的请求体（只有代理记录显示 `requestData`）。原料留在解析层，差异记 §11；**不生成 `match.body` 条件**这条仍照办（延续拒绝语义） |
| URL 的 host 与端口 | **不写入 `match.host`**，一律留空串（= 任意 host、任意端口）；host 只保留在 `source.url` 里供展示与排查。这是 Q2 的裁决结果，不是解析缺陷 |
| `request.url` 含 fragment | 丢弃 `#` 之后部分 |
| Query 重复键 | 保留为多值条件，`multiValue` 取 `any`（与 `shared/url.ts:74` `queryParts` 一致） |
| 非 http(s) 协议 | 逐条拒并跳过，报 `harUnsupportedProtocol`（detail 带协议名）。**不按卡片字面用 `toAbsoluteTarget`**：它只认 `scheme://` 形态，`data:image/png;base64,…` 会被补成 `http://data:…` 后报 `invalid` 而不是「协议不支持」，既拒不掉也读不出协议名；改读 `parseLooseUrl` 的 `protocol`，它与后面派生 path 读的是同一个 URL 对象 |
| 静态资源 entry（js/css/图片） | 默认跳过并计数，提供「包含静态资源」开关（默认关）——否则一次页面 HAR 灌进几百条无意义记录 |
| `response.status === 0` | 跳过（HAR 里表示请求未完成的常见情况） |
| 导入后是否自动跑稳定性分析 | **不自动**。结果页提供「分析并应用建议」按钮，由用户点。附录 B.3 原文「导入后执行一次场景内稳定性分析」与本裁决不一致，需回写 |
| 场景分组 | 一个文件一个场景，名称取文件名（评审 §11 对 4.4.5 的修订建议） |

**落地状态（R4C-21，2026-11-20）**：表里的形态由 `src/main/service/mock.har.ts` 读到位——`readHarText(text, byteSize)` 是包级信封，四条顺序与 `readMockPackText` 一致（字节 → 非空 → JSON → 形状），「按内容分派两种包」就落在这一步：顶层带 `format` 的那一份是规则包，detail 直接写破 `this is a rule pack, not a HAR`，两边互不吃对方的闸门；`parseHarEntries(entries)` 逐条判形状，`status===0`、缺 `response`、`entry` 压根不是对象三种都归 `harNoResponse`（detail 分写 `response is …` 与 `entry is …`，看得出是哪种），`content.text` 缺失但 `size>0` 归 `harBodyUnreadable`（detail 带 `size` 与 `mimeType`）。表里剩下的行不在这张卡：`postData.params` 与 fragment 只做到「读进来、留原料」，协议白名单、`match.host` 留空、query 拆分与 `ignoreKeys` 属 R4C-22，解码与 2MB 属 R4C-23，`harEntryLimit` 与静态资源开关、建议接线属 R4C-24。

四处按实现定稿，都不是卡片没写的新规则，但值得记账：

- **fragment 截在解析层，而不是留给 `shared/url.ts`**。`queryParts`（`src/shared/url.ts:73-82`）只把出现在 `?` 之后的 `#` 当终止符，而 `new URL()` 把 `#` 之后全归给 hash——`x#seg?token=1` 这种串在引擎的两条读法里本来就有两种答案。截完之后存下来的 `url` 只剩一种读法，映射层不再碰 `#` 就不可能分叉；用例把「不截就会分叉」和「截完两种读法一致」两头都钉了。
- **方法大小写不在这层判**。`normalizeMethod`（`src/shared/mock.models.ts:313-316`）已经是「trim + 大写 + 空即 ANY」的唯一口径，解析层交出原样字符串；在这一层再 upper 一次就是第二条标准。
- **缺 `request` 的 entry 不跳过**。那只是 URL 为空，属阶段二 `matchMissing` 的话。这一层只回答「有没有可 Mock 的响应」，多判一次就会让同一份文件在两处各有一套跳过理由。
- **`status` 认数字也认纯数字串**。`"200"` 被读成 0 就是静默丢条目（用户看到的是「导入成功但少了几条」），比多读一个数难查；非数字的非空值仍落 0，即 `harNoResponse`，detail 里看得见。

**落地状态（R4C-22，2026-11-20）**：映射层 `mapHarEntries(entries, { analyzedAt })` 接在同一份文件末尾，只把「够得着真实导出形态」的原料换成包侧记录，三件事各自有主人——**match 一律由既有派生层 `analyzeMatchStability` 产出**（自己拆一遍 URL 就会与匹配引擎的归一化结果分叉，症状正是「导入了却不命中」）；**响应体只做「存得对」**（base64 原样存 + `bodyEncoding='base64'`，引擎按 base64 发得出去，解码属 R4C-23）；**跳过只判协议**，URL 为空仍交给阶段二 `matchMissing`。表里 `match.host` 留空串、E2 剔进 `ignoreKeys`、ID 段只出建议、不生成 `match.body`，四条在本卡全部有断言。

四处按实现定稿：

- **输出是 `MockPackRecord`（`{ match?, response, source }`），不是本节早先写的 `MockRecord[]`**。HAR 条目因此直接进既有的包链路——阶段二校验（R4C-10/11）、归一化与默认值（R4C-12）、时间戳注入（R4C-16）、写库（R4C-18）、上限复核（R4C-20）一件都不必重写；反过来要是这里造一条完整 `MockRecord`，就得同时决定 ID、`ruleId`、`name` 与两个时间戳怎么来，而那五个答案在写库那一步已经有了。
- **`url` / `matchFingerprint` / `name` / `id` / 时间戳一概不填**。前两个是派生值（`mock.pack.ts:55`），手填等于绕过查重；`name` 由 R4C-12 的默认值补齐、走 `packFieldDefaulted` 那条 notes 通道，比在这里按 URL 编一个更可查。用例直接钉住「记录只有 `match`/`response`/`source` 三个键」。
- **逐条分析，不把整份文件当一组**。实测反证：两份同接口 entry（`/v1/orders/123456?filter=a` 与 `/v1/orders/789012?filter=b`）攒成一组会得到 `path=/v1/orders/*` + `pathType=glob` + `ignoreKeys=[filter, token]`，而 B.3 明令单份 HAR 不做 E1 自动忽略、不做 Path 自动参数化；逐条才是 `path=/v1/orders/123456` 精确匹配、只有 E2 那批高风险键进 `ignoreKeys`。**反样本材取 `filter` 而不是 `page`**：`page` 属 E5 语义键，优先级高于 E1，两种口径下都留在条件里，用它做对照用例会假绿。
- **协议白名单不照卡片字面用 `toAbsoluteTarget`**，改读 `parseLooseUrl` 的 `protocol`（理由见上表那行），并新增条目级跳过码 `harUnsupportedProtocol`（§8）——它属「这条不要」而不是「这条读不出」，与解析层那两个码各数各的。

**落地状态（R4C-23，2026-11-20）**：响应体判定接在映射层的 `bodyOf`（`src/main/service/mock.har.ts:317`），`responseOf` 因此改形状——要么交出完整的 `MockResponseDef`，要么交出一句「读不出」的 detail；跳过明细要能指回文件里的 entry 下标，所以这个岔口留在逐条循环里，不在纯函数里抛。四种正文形态各有归宿：文本档 base64 解成文本、binary 档 base64 原样存、解不出 UTF-8 的降级成 binary、判成 binary 却没有 base64 标记的逐条跳过。

三处按实现定稿：

- **解码放在映射层，不回填解析层**。判据是 `inferBodyType(contentType)`，而 `contentType` 是「响应头 `content-type` 优先、`content.mimeType` 其次」（R4C-22 那条定稿的延续）；解析层只看得见 `mimeType`，把解码放进去就等于为同一件事准备两套 content-type 读法，症状是「编辑器里显示成 JSON 的那条，导入时被当二进制」。

- **降级而不是丢弃**：`mimeType: text/plain` 却解不出合法 UTF-8 的样本仍是一条有效响应（charset 报错的 UTF-16 正文就属这类）。按 binary 存还能发出原字节；把它跳掉会让用户凭空少一条能用的规则，而跳过数恰好掩盖了「这份文件的 mimeType 不可信」这件事。

- **`text === ''` 要早退**：空正文没有可解的字节，204 那类照样导入。缺这一句，「判成 binary 却没有 base64 标记」会把空正文一并算成读不出——用户看到的是「导入成功但 204 全被跳了」，比多收几条 204 难查得多。

**未接线**：R4C-22~23 之后仍是**零调用方**——`importHar` 是空结果桩（`src/main/router/appmock.router.ts:479-483`），解析与映射两层都没有入口；「一文件一场景、名称取文件名」属服务层与渲染层（R4C-25~28），分派、`harEntryLimit`、静态资源开关与建议接线属 R4C-24。**fixture 仍是手工形态样本**：任务拆分「前置动作」里那份 Chrome / Firefox / Charles 真实导出尚未采集，所以 §9 这张表钉住的是「表里写的形状」，不是「真实工具的实际写法」——R4C-23 的四种正文形态同样如此，尤其是「判成 binary 却没有 base64 标记」这一种到底在真实导出里占多少，只有采到样本才知道。

## 13. 风险与取舍

| 风险 | 影响 | 应对 |
|---|---|---|
| 导入绕过写入管线导致「导入成功但不生效」 | 高 | 6.2 的复用方案 + 「导入后真实请求必须命中」的硬断言 |

| 50MB 文件内存峰值 | 中 | **桌面端边拼边写盘**（[6.3](#63-导出组装)/[D2](#d2-文件写出主进程组装--主进程弹框落盘返回值三态)，实测收尾活堆 +0.2MB 且与包大小无关）+ 上限 5,000 条 + 压力用例设阈值；「分片拼接」本身不解耦——字符串出口实测 ≈2× 包体积 |
